Memahami FastAPI untuk AI/Machine Learning

Cara mengubah model yang hanya hidup di notebook menjadi layanan web yang bisa dipanggil aplikasi lain: validasi input, dokumentasi otomatis, concurrency, streaming ala LLM, dynamic batching, keamanan, testing, sampai deployment. Dijelaskan lewat analogi restoran, diagram, 12 simulasi interaktif, dan kode Python yang sudah dijalankan. Estimasi waktu belajar ± 4 jam.

🎯 Tujuan belajar Setelah modul ini kamu bisa membungkus model machine learning menjadi layanan HTTP yang rapi: menerima input yang divalidasi otomatis, memuat model sekali saat server menyala, menjawab banyak klien bersamaan tanpa saling memblokir, mengalirkan hasil secara streaming, mengelompokkan permintaan dengan dynamic batching, melindunginya dengan autentikasi dan rate limit, mengujinya dengan pytest, dan membawanya ke container.
Prasyarat: Python dasar (fungsi, kelas, dictionary, type hint sederhana) dan pernah memakai model scikit-learn (atau sejenisnya) di notebook. Tidak perlu pengalaman web sebelumnya; semua istilah web dijelaskan dari nol.

1. Dari Notebook ke Layanan: Kenapa Perlu API?

Bayangkan kamu sudah melatih model yang akurasinya bagus. Di notebook, memakainya mudah: model.predict(x). Masalahnya, model itu hanya hidup di laptopmu. Aplikasi mobile, situs web, atau sistem milik tim lain tidak bisa (dan tidak seharusnya) menjalankan notebook-mu. Mereka butuh cara memanggil model dari jauh, lewat jaringan, dengan bahasa yang sama-sama dimengerti. Cara paling umum adalah API berbasis HTTP: klien mengirim data (biasanya JSON), server menjalankan model, lalu membalas dengan hasil prediksi.

Karena sebagian besar riset dan pelatihan model dilakukan dengan Python, kita ingin lapisan layanannya juga Python, supaya model tidak perlu ditulis ulang. Di sinilah FastAPI masuk. FastAPI adalah web framework Python modern yang memanfaatkan type hint untuk tiga hal sekaligus: membaca dan memvalidasi input, menghasilkan dokumentasi interaktif otomatis, dan mengatur eksekusi yang efisien.

Analogi: restoran dengan dapur AI

Analogi ini akan kita pakai berulang. Perhatikan satu hal: dapur (model) tidak peduli bagaimana pelanggan memesan, dan pelayan tidak perlu tahu cara memasak. Memisahkan keduanya membuat model bisa diganti tanpa mengubah cara klien memesan, dan kontrak pesanan bisa diubah tanpa melatih ulang model.

2. Bekal: HTTP, JSON, dan REST

FastAPI menyembunyikan banyak detail jaringan, tetapi untuk men-debug layanan model kamu perlu paham tiga hal: bagaimana pesan HTTP tersusun, apa arti kode status, dan bagaimana JSON dipetakan ke tipe Python. Bagian ini singkat, tetapi hampir setiap pesan error yang kamu temui nanti akan merujuk ke sini.

Anatomi percakapan HTTP

HTTP adalah percakapan sederhana: klien bertanya (request), server menjawab (response). Keduanya adalah teks dengan struktur yang sama: baris pertama (apa yang diminta atau hasilnya), beberapa header (metadata, seperti keterangan di amplop surat), baris kosong, lalu body (isi surat).

RequestMethod (GET, POST, …) menyatakan niat. Path (/prediksi) menyatakan alamat sumber daya. Query string (?batas=5) berisi parameter opsional. Header membawa metadata seperti Content-Type dan X-API-Key. Body membawa data, biasanya JSON.
ResponseStatus code (200, 422, …) meringkas hasilnya dalam satu angka. Header menjelaskan isi balasan. Body berisi hasil, misalnya JSON prediksi atau penjelasan error.

3. Hello FastAPI & Dokumentasi Otomatis


Saatnya menulis layanan pertama. Targetnya sengaja kecil: dua endpoint, supaya kita bisa fokus pada bentuk aplikasi FastAPI sebelum menambahkan model. Simpan kode berikut sebagai hello.py.


hello.pyPython
from fastapi import FastAPI

app = FastAPI()  #+


@app.get("/")  #+
def root():
    return {"pesan": "Halo dari FastAPI!"}


@app.get("/kuadrat/{n}")
def kuadrat(n: int):  #+
    return {"n": n, "hasil": n * n}


Tiga ide inti ada di file sekecil ini:



  
🏭app = FastAPI()Membuat objek aplikasi. Semua endpoint didaftarkan ke objek ini. Nama variabel app hanya konvensi, tetapi nanti kita sebut namanya saat menyalakan server.

  
🏷️@app.get("/")Decorator yang mendaftarkan fungsi di bawahnya sebagai path operation: ketika ada request GET ke path /, jalankan fungsi ini. Ganti get dengan post, put, delete sesuai kebutuhan.

  
🧬n: intType hint bukan sekadar hiasan. FastAPI membacanya untuk memutuskan dari mana nilai diambil (di sini dari path {n}), mengubah tipenya, dan menolak yang tidak cocok.




Fungsi cukup mengembalikan dict biasa. FastAPI yang mengubahnya menjadi JSON, menambahkan header Content-Type, dan menulis status 200. Sebelum menyalakan server, kita bisa mencobanya langsung dari Python memakai TestClient (lebih jauh di Bagian 14):


coba_hello.pyPython
from fastapi.testclient import TestClient
from hello import app

c = TestClient(app)
for path in ["/", "/kuadrat/7", "/kuadrat/abc", "/tidak-ada"]:
    r = c.get(path)
    print(f"GET {path} -> {r.status_code} {r.json()}")


Keluaran (dijalankan: Python 3.13, FastAPI 0.162)
GET / -> 200 {'pesan': 'Halo dari FastAPI!'}
GET /kuadrat/7 -> 200 {'n': 7, 'hasil': 49}
GET /kuadrat/abc -> 422 {'detail': [{'type': 'int_parsing', 'loc': ['path', 'n'], 'msg': 'Input should be a valid integer, unable to parse string as an integer', 'input': 'abc'}]}
GET /tidak-ada -> 404 {'detail': 'Not Found'}


Perhatikan tiga hal dari keluaran: (1) /kuadrat/7 menghasilkan 49; (2) /kuadrat/abc otomatis ditolak dengan 422 tanpa satu baris pun kode validasi buatan kita; (3) path yang tidak terdaftar menghasilkan 404. Detail pesan 422 akan kita bedah di Bagian 4 dan 5.

Saat sebuah fungsi endpoint punya parameter, FastAPI harus memutuskan: nilai ini datang dari mana? Aturannya sederhana dan konsisten, sehingga kamu cukup membaca tanda tangan fungsi untuk tahu bentuk API-nya.



  
Kalau parameter…Maka FastAPI membacanya dari…Contoh

  
namanya muncul di path {...}Path (bagian dari alamat)/kuadrat/{n} → n: int

Contoh di bawah menghitung BMI dan mencari data. Perhatikan Query(...) yang menambahkan batas nilai:


s1_params.pyPython
from fastapi import FastAPI, Query

app = FastAPI()


@app.get("/bmi")
def bmi(berat_kg: float, tinggi_cm: float = 170):  #+
    """berat_kg wajib (tak punya default), tinggi_cm opsional."""
    tinggi_m = tinggi_cm / 100
    return {"bmi": round(berat_kg / tinggi_m**2, 1)}


@app.get("/cari")
def cari(q: str, batas: int = Query(default=5, ge=1, le=50)):  #+
    return {"kata_kunci": q, "batas": batas}

🕳️ Lubang yang lolos dari validasi tipe
  Validasi tipe hanya menjamin "ini angka", bukan "ini angka yang masuk akal". Untuk endpoint /bmi di atas, tiga input ini lolos validasi dan membuat server melempar error 500:
  
    
    
  • berat_kg=nan dan berat_kg=inf: float Python memang menerima nan dan inf, lalu JSON tidak bisa mengungkapkannya.
    • 
    
  • tinggi_cm=0: lolos sebagai angka, lalu ZeroDivisionError saat dibagi.
    • 
  

  Dalam layanan ML, input liar seperti inilah yang diam-diam merusak prediksi atau menjatuhkan server. Selalu tambahkan batas domain.



Perbaikannya: beri batas dengan gt, le dan matikan nan/inf dengan allow_inf_nan=False. Sekaligus kita pakai gaya Annotated yang dianjurkan dokumentasi FastAPI terbaru (tipe dan metadata dipisah dari nilai default):

from typing import Annotated

from fastapi import FastAPI, Query

app = FastAPI()


@app.get("/bmi")
def bmi(
    berat_kg: Annotated[float, Query(gt=0, le=500, allow_inf_nan=False)],  #+
    tinggi_cm: Annotated[float, Query(gt=0, le=300, allow_inf_nan=False)] = 170,  #+
):
    tinggi_m = tinggi_cm / 100
    return {"bmi": round(berat_kg / tinggi_m**2, 1)}

5. Pydantic: Validasi Request Body


Query string cocok untuk beberapa nilai sederhana. Input model ML hampir selalu lebih kaya: banyak fitur, objek bersarang, daftar. Untuk itu kita pakai Pydantic. Kamu mendeskripsikan bentuk data sebagai kelas; Pydantic memeriksa, mengubah tipe, dan menolak data yang tidak cocok. Anggap Pydantic sebagai pelayan yang teliti: ia tidak mau meneruskan pesanan yang formulirnya tidak lengkap ke dapur.


skema.pyPython
from pydantic import BaseModel, Field, field_validator


class BungaIris(BaseModel):
    panjang_sepal: float = Field(gt=0, le=15, description="cm")  #+
    lebar_sepal: float = Field(gt=0, le=15, description="cm")
    panjang_petal: float = Field(gt=0, le=15, description="cm")
    lebar_petal: float = Field(gt=0, le=15, description="cm")

    @field_validator("lebar_petal")  #+
    @classmethod  #+
    def petal_tak_lebih_panjang_dari_sepal(cls, v, info):
        if v > info.data.get("panjang_sepal", v) * 2:
            raise ValueError("lebar_petal tidak masuk akal dibanding panjang_sepal")
        return v


class Prediksi(BaseModel):
    kelas: str
    probabilitas: dict[str, float]
    versi_model: str

  • Field(gt=0, le=15) memasang batas domain: panjang sepal bunga iris tidak mungkin negatif atau 15 cm lebih. Daftar batas lain: ge, lt, min_length, max_length, pattern.

main.pyPython
from contextlib import asynccontextmanager

import joblib
import numpy as np
from fastapi import Depends, FastAPI, Header, HTTPException, Request

from skema import BungaIris, Prediksi

VERSI = "iris-rf-1.0"
API_KEYS = {"rahasia-123"}


@asynccontextmanager
async def lifespan(app: FastAPI):
    # Dijalankan SEKALI saat server menyala
    paket = joblib.load("model_iris.joblib")  #+
    app.state.model = paket["model"]  #+
    app.state.kelas = paket["kelas"]  #+
    yield  #+
    # Dijalankan saat server mati (bersih-bersih)
    app.state.model = None


app = FastAPI(title="Layanan Iris", version="1.0.0", lifespan=lifespan)


def ambil_model(request: Request):
    return request.app.state


def cek_api_key(x_api_key: str = Header()):
    if x_api_key not in API_KEYS:
        raise HTTPException(status_code=401, detail="API key tidak valid")


@app.get("/health")
def health(state=Depends(ambil_model)):
    return {"status": "ok", "model_siap": state.model is not None}


@app.post("/prediksi", response_model=Prediksi, dependencies=[Depends(cek_api_key)])  #+
def prediksi(bunga: BungaIris, state=Depends(ambil_model)):  #+
    x = np.array([[bunga.panjang_sepal, bunga.lebar_sepal,  #+
                   bunga.panjang_petal, bunga.lebar_petal]])  #+
    proba = state.model.predict_proba(x)[0]
    terbaik = int(proba.argmax())
    return Prediksi(
        kelas=state.kelas[terbaik],
        probabilitas={k: round(float(p), 3) for k, p in zip(state.kelas, proba)},
        versi_model=VERSI,
    )


Mari bedah bagian-bagian pentingnya:



  
① lifespan: memuat sekaliKode sebelum yield berjalan sekali saat server menyala (sebelum menerima request pertama). Kode setelah yield berjalan saat server mati. Model disimpan di app.state, yaitu tempat resmi untuk menaruh objek yang dipakai bersama. Ini menggantikan @app.on_event("startup") yang sudah tidak dianjurkan.

  
② Fungsi def, bukan async defInferensi scikit-learn adalah komputasi yang memblokir. Dengan def, FastAPI menjalankannya di threadpool sehingga request lain tetap terlayani. Alasan lengkapnya ada di Bagian 8.

④ Konversi ke tipe Pythonfloat(p) dan int(...) mengubah tipe NumPy menjadi tipe bawaan Python supaya bisa menjadi JSON. round(..., 3) merapikan tampilan.

8. async def vs def: Memahami Event Loop


Ini topik yang paling sering disalahpahami pengguna FastAPI, dan bagi layanan ML salah paham di sini bisa berarti server yang "hidup tapi macet". Kabar baiknya, ide dasarnya bisa dipahami lewat sebuah kafe.



Analogi: kafe dengan satu barista







Mari terjemahkan. Semua kode async def berjalan di satu event loop (si barista) yang hanya bisa mengerjakan satu hal pada satu waktu, tetapi bisa berpindah ke pekerjaan lain setiap kali menemui kata await. Kata kunci await artinya: "saya akan menunggu hal ini; silakan layani yang lain dulu". Kalau di dalam async def kamu menjalankan kode yang tidak memakai await tetapi lama (time.sleep, model.predict, membaca berkas besar, requests.get), si barista terpaku dan seluruh server berhenti melayani sampai selesai.


Fungsi def biasa diperlakukan berbeda: FastAPI menjalankannya di threadpool terpisah (bawaannya 40 thread pada percobaan kami), sehingga event loop tetap bebas. Mari buktikan dengan percobaan nyata: tiga endpoint yang sama-sama "bekerja" 0,2 detik, dipanggil 10 klien bersamaan, plus satu pola gabungan.


async_demo.pyPython
import asyncio
import time

from fastapi import FastAPI
from fastapi.concurrency import run_in_threadpool

app = FastAPI()


@app.get("/async-memblokir")
async def async_memblokir():
    time.sleep(0.2)            # blocking di dalam async def: MEMBLOKIR event loop  #+

9. Dependency Injection dengan Depends


Lihat kembali main.py: dua endpoint sama-sama butuh akses ke model, dan satu butuh pemeriksaan API key. Menyalin kode yang sama ke setiap fungsi akan cepat berantakan. FastAPI menyelesaikannya dengan dependency injection: kamu menulis sebuah fungsi kecil yang menghasilkan sesuatu yang dibutuhkan, lalu endpoint cukup menyatakan "saya butuh itu" lewat Depends(...).


Analogi dapur: koki tidak pergi ke pasar sendiri tiap kali butuh bawang. Ia bilang "saya butuh bawang" dan bagian logistik menyediakannya. Kalau suatu hari bawang diganti bawang organik, koki tidak perlu diberi tahu.



  
Yang umum disediakan lewat DependsAkses model / tokenizer, pemeriksaan API key atau token, sesi database, pagination, konfigurasi, rate limiter, logger per request.

  
Manfaat utama(1) tidak ada duplikasi kode; (2) dokumentasi OpenAPI ikut tahu (misalnya header X-API-Key muncul di /docs); (3) sangat mudah diuji karena dependency bisa diganti (dependency_overrides).





Tiga pola yang paling berguna


Pola 1: fungsi pemasok biasa. ambil_model dan cek_api_key di main.py adalah contohnya. Untuk pemeriksaan yang tidak menghasilkan nilai (hanya menolak atau meloloskan), taruh di dependencies=[Depends(...)] pada dekorator, seperti yang kita lakukan pada /prediksi. Pola ini juga bisa dipasang sekaligus untuk satu kelompok endpoint lewat APIRouter(dependencies=[...]) (lihat studi kasus di Bagian 16).


Pola 2: dependency dengan yield untuk sumber daya yang harus dibuka lalu ditutup per request, seperti sesi database. Kode setelah yield dijamin berjalan di akhir request:

@app.get("/pakai-sesi")

Model ML jarang hanya menerima angka. Sering kali inputnya berkas: CSV berisi ratusan baris, foto untuk klasifikasi, rekaman suara. Pekerjaan lain, seperti mencatat log atau mengirim notifikasi, tidak perlu membuat klien menunggu. Dan ada kebutuhan yang berlaku untuk semua endpoint, misalnya mengukur waktu proses. import csv
import io
import time
from contextlib import asynccontextmanager

import joblib
import numpy as np
from fastapi import BackgroundTasks, FastAPI, HTTPException, Request, UploadFile
from PIL import Image, UnidentifiedImageError


@asynccontextmanager
async def lifespan(app: FastAPI):
    app.state.paket = joblib.load("model_iris.joblib")
    yield


app = FastAPI(lifespan=lifespan)


@app.middleware("http")  #+
async def catat_waktu(request: Request, call_next):  #+
    mulai = time.perf_counter()
    response = await call_next(request)
    response.headers["X-Waktu-Proses-ms"] = f"{(time.perf_counter() - mulai) * 1000:.1f}"  #+
    return response


def tulis_log(baris: str):
    with open("prediksi.log", "a") as f:
        f.write(baris + "\n")


@app.post("/unggah-csv")
def unggah_csv(berkas: UploadFile, tugas: BackgroundTasks):  #+
    if not (berkas.filename or "").endswith(".csv"):
        raise HTTPException(status_code=415, detail="Hanya menerima .csv")
    isi = berkas.file.read().decode("utf-8")
    baris = list(csv.DictReader(io.StringIO(isi)))
    X = np.array([[float(b[k]) for k in ("ps", "ls", "pp", "lp")] for b in baris])
    paket = app.state.paket
    kelas = [paket["kelas"][i] for i in paket["model"].predict(X)]
    tugas.add_task(tulis_log, f"{berkas.filename}: {len(kelas)} baris")  #+
    return {"jumlah": len(kelas), "hasil": kelas}


@app.post("/unggah-gambar")
def unggah_gambar(berkas: UploadFile):  #+
    try:  #+
        gambar = Image.open(berkas.file).convert("L")  #+
    except UnidentifiedImageError:  #+
        raise HTTPException(status_code=415, detail="Berkas bukan gambar yang dikenali")  #+
    arr = np.asarray(gambar, dtype=np.float32) / 255.0
    return {"ukuran": gambar.size, "kecerahan_rata2": round(float(arr.mean()), 3)}

11. Streaming & LLM


Pernah memperhatikan bagaimana ChatGPT dan sejenisnya menampilkan jawaban kata demi kata? Itu streaming. Alasannya bukan sekadar gaya. Model bahasa menghasilkan token satu per satu, dan jawaban penuh bisa memakan 10–30 detik. Kalau server menunggu semuanya selesai baru membalas, pengguna menatap layar kosong selama itu. Dengan streaming, kata pertama muncul dalam hitungan milidetik, sehingga layanan terasa cepat meski total waktunya sama.


Analogi: bandingkan surat dan percakapan telepon. Pada surat, kamu menunggu penulisnya menyelesaikan seluruh isi baru menerimanya. Pada telepon, kata pertama sudah terdengar sebelum kalimat selesai diucapkan.


📏 Dua metrik yang membedakan streaming
  TTFT (time to first token): waktu sampai potongan pertama tiba, ukuran kenyamanan pengguna. Total latency: waktu sampai semua selesai, ukuran kerja mesin. Streaming memperbaiki yang pertama; yang kedua tidak berubah.




Streaming dengan FastAPI


Kuncinya adalah generator: fungsi yang yield potongan demi potongan. Kita tiru LLM dengan generator yang mengeluarkan satu kata tiap 50 ms. Ada dua cara menyajikannya. Pertama, StreamingResponse yang tersedia di semua versi. Kedua, pada FastAPI versi baru, EventSourceResponse yang otomatis membungkus setiap yield menjadi format Server-Sent Events (SSE), standar yang dipahami langsung oleh EventSource di browser.


stream_demo.pyPython
import asyncio

from fastapi import FastAPI
from fastapi.responses import EventSourceResponse, StreamingResponse

app = FastAPI()
JAWABAN = "FastAPI memudahkan kita menyajikan model sebagai layanan web".split()


async def hasilkan_token():
    """Meniru LLM: token keluar satu per satu."""
    for kata in JAWABAN:
        await asyncio.sleep(0.05)
        yield kata + " "


@app.get("/stream-teks")
async def stream_teks():
    return StreamingResponse(hasilkan_token(), media_type="text/plain")  #+


@app.get("/stream-sse", response_class=EventSourceResponse)  #+
async def stream_sse():
    async for token in hasilkan_token():
        yield {"token": token}  #+

12. Dynamic Batching: Menaikkan Throughput


Satu fakta tentang hardware modern yang mengubah cara kita menyajikan model: memproses 64 input sekaligus hampir semurah memproses 1 input. GPU (dan juga library vektor di CPU) punya biaya tetap yang besar untuk setiap panggilan (memindahkan data, meluncurkan kernel) dan biaya per-item yang kecil. Kalau setiap request dijalankan sendiri-sendiri, kita membayar biaya tetap itu berulang kali.


Analogi: ojek vs angkot. Ojek berangkat begitu satu penumpang naik: cepat untuk si penumpang, tetapi jalan raya penuh motor setengah kosong. Angkot menunggu sebentar sampai penuh atau sampai batas waktu tertentu, lalu berangkat membawa banyak penumpang sekaligus. Jalan lebih lengang (throughput tinggi), tetapi tiap penumpang menanggung sedikit waktu tunggu (latensi).








Implementasi dengan asyncio.Queue


Idenya: setiap request menaruh inputnya ke antrean bersama sebuah Future (janji hasil), lalu await janji itu. Sebuah tugas latar mengumpulkan item dari antrean hingga penuh atau kehabisan waktu, menjalankan model sekali untuk semuanya, lalu mengisi setiap janji dengan hasilnya. Model tiruan di bawah memakai biaya 20 ms + 1 ms per item untuk meniru perilaku GPU.


pembatch.pyPython
import asyncio
import time
from contextlib import asynccontextmanager

from fastapi import FastAPI


class Pembatch:
    """Mengumpulkan permintaan yang datang berdekatan lalu memprosesnya sekaligus."""

    def __init__(self, fungsi_model, maks_batch=16, maks_tunggu=0.01):
        self.fungsi_model = fungsi_model      # list[input] -> list[output]
        self.maks_batch = maks_batch
        self.maks_tunggu = maks_tunggu        # detik
        self.antrian: asyncio.Queue = asyncio.Queue()
        self.tugas: asyncio.Task | None = None

    def mulai(self):
        self.tugas = asyncio.create_task(self._loop())

    async def berhenti(self):
        self.tugas.cancel()

    async def prediksi(self, x):
        loop = asyncio.get_running_loop()
        masa_depan = loop.create_future()  #+
        await self.antrian.put((x, masa_depan))  #+
        return await masa_depan               # menunggu sampai batch-nya selesai  #+

    async def _loop(self):
        loop = asyncio.get_running_loop()
        while True:
            batch = [await self.antrian.get()]
            batas = loop.time() + self.maks_tunggu
            while len(batch) < self.maks_batch:  #+
                sisa = batas - loop.time()
                if sisa <= 0:
                    break
                try:
                    batch.append(await asyncio.wait_for(self.antrian.get(), sisa))
                except asyncio.TimeoutError:
                    break
            masukan = [x for x, _ in batch]
            try:  #+
                keluaran = await loop.run_in_executor(None, self.fungsi_model, masukan)  #+
                for (_, f), y in zip(batch, keluaran):
                    f.set_result(y)
            except Exception as e:            # jangan biarkan klien menunggu selamanya  #+
                for _, f in batch:  #+
                    f.set_exception(e)  #+


def model_palsu(daftar):
    """Meniru GPU: biaya tetap 20 ms per panggilan + 1 ms per item."""
    time.sleep(0.020 + 0.001 * len(daftar))
    return [x * 2 for x in daftar]


@asynccontextmanager
async def lifespan(app: FastAPI):
    app.state.pembatch = Pembatch(model_palsu, maks_batch=16, maks_tunggu=0.01)
    app.state.pembatch.mulai()
    yield
    await app.state.pembatch.berhenti()


app = FastAPI(lifespan=lifespan)


@app.get("/gandakan/{x}")
async def gandakan(x: int):
    return {"hasil": await app.state.pembatch.prediksi(x)}


Beberapa detail penting yang membedakan implementasi ini dari versi naif:


    
  
  • Setiap request punya Future-nya sendiri, sehingga hasil batch bisa dibagikan ke pemilik yang tepat tanpa tertukar.
    • 
  
  • run_in_executor menjalankan model di thread, jadi event loop tetap bebas menerima request baru selagi batch diproses (Bagian 8).
    • 
  
  • Penanganan error: bila model melempar exception, semua request dalam batch itu ikut gagal dengan error tersebut. Tanpa blok except, tugas latar akan mati dan semua klien berikutnya menunggu selamanya.
    • 
  
  • Batas waktu tunggu maks_tunggu menjaga latensi tetap terbatas: request tunggal di jam sepi tetap berangkat setelah paling lama 10 ms.
    • 



Kita uji dua hal: apakah hasilnya benar (setiap klien mendapat jawabannya sendiri) dan apakah throughput naik. Uji kedua melepas 64 request sekaligus untuk berbagai ukuran batch:


ukur_batch.pyPython
import asyncio, time
from pembatch import Pembatch, model_palsu

async def uji(maks_batch, n=64):
    pb = Pembatch(model_palsu, maks_batch=maks_batch, maks_tunggu=0.01)
    pb.mulai()
    lat = []
    async def satu(i):
        t = time.perf_counter()
        y = await pb.prediksi(i)
        lat.append(time.perf_counter() - t)
        assert y == i * 2
    t0 = time.perf_counter()
    await asyncio.gather(*[satu(i) for i in range(n)])
    total = time.perf_counter() - t0
    await pb.berhenti()
    lat.sort()
    print(f"maks_batch={maks_batch:2d}  total {total*1000:6.0f} ms  throughput {n/total:6.0f} req/s  latensi rata2 {sum(lat)/len(lat)*1000:6.0f} ms  p95 {lat[int(.95*len(lat))-1]*1000:6.0f} ms")

for mb in (1, 4, 16, 64):
    asyncio.run(uji(mb))

Rate limiting: jangan biarkan satu klien menghabiskan semuanya


Inferensi itu mahal. Satu klien yang menembak tanpa henti (karena bug loop, atau memang sengaja) bisa membuat semua orang lain kehabisan jatah. Algoritma klasiknya adalah token bucket: setiap klien punya ember berisi token yang terisi pelan-pelan; setiap request mengambil satu token; ember kosong berarti 429 Too Many Requests. Ember memungkinkan lonjakan singkat (sebanyak kapasitas) sambil membatasi laju rata-rata (sebanyak laju isi ulang).

# 6. Rate limit: token bucket per klien (in-memory, satu proses saja!)
class TokenBucket:
    def __init__(self, kapasitas: int, isi_per_detik: float):
        self.kapasitas, self.laju = kapasitas, isi_per_detik
        self.token, self.terakhir = float(kapasitas), time.monotonic()

    def boleh(self) -> bool:
        sekarang = time.monotonic()  #+
        self.token = min(self.kapasitas, self.token + (sekarang - self.terakhir) * self.laju)  #+
        self.terakhir = sekarang  #+
        if self.token >= 1:  #+
            self.token -= 1  #+
            return True  #+
        return False  #+


ember: dict[str, TokenBucket] = {}


def batasi(request: Request):  #+
    ip = request.client.host  #+
    b = ember.setdefault(ip, TokenBucket(kapasitas=3, isi_per_detik=1))  #+
    if not b.boleh():  #+
        raise HTTPException(status_code=429, detail="Terlalu banyak permintaan", headers={"Retry-After": "1"})  #+


@app.get("/terbatas", dependencies=[Depends(batasi)])
def terbatas():
    return {"ok": True}

15. Deployment & Kapasitas


Kode sudah jalan dan teruji. Bagaimana menaruhnya agar bisa dipakai banyak orang, andal, dan tidak kehabisan memori? Bagian ini menjelaskan komponennya, lalu memberimu alat hitung kapasitas sederhana.








Worker: memanfaatkan lebih dari satu inti


Satu proses Python hanya efektif memakai satu inti untuk kode Python (karena GIL). Untuk memakai banyak inti, jalankan banyak proses worker. Uvicorn mendukungnya langsung dengan --workers N. Berikut percobaan nyata dengan --workers 2 pada layanan Iris:

Dua hal terlihat jelas. Pertama, setiap worker adalah proses terpisah yang memuat model sendiri (log "Application startup complete" muncul dua kali, yang berarti lifespan dijalankan dua kali). Kedua, memori dikalikan jumlah worker. Model Iris kecil, sehingga sebagian besar dari 162 MB itu adalah NumPy, scikit-learn, dan interpreter. Untuk model 2 GB dengan 4 worker, kamu butuh ≥ 8 GB hanya untuk model.


⚠️ Thread yang bersembunyi
  NumPy, PyTorch, dan library BLAS sering memakai banyak thread sendiri untuk satu operasi. Jika kamu menjalankan 4 worker dan tiap worker memakai 8 thread di mesin 8 inti, terjadi oversubscription: 32 thread berebut 8 inti dan semuanya melambat. Atur jumlah thread library (misalnya variabel lingkungan OMP_NUM_THREADS) agar worker × thread ≤ inti.



Alternatif yang juga sangat umum: menjalankan satu proses per container dan membiarkan orkestrator (Kubernetes, ECS, Cloud Run) menambah replika. Cara ini menyederhanakan penjadwalan sumber daya dan pemulihan dari kegagalan. Pada mesin GPU, pola yang lazim adalah satu proses per GPU.

from pydantic import BaseModel, Field


class PermintaanTeks(BaseModel):
    teks: str = Field(min_length=3, max_length=1000, examples=["pelayanannya ramah sekali"])


class HasilSentimen(BaseModel):
    label: str
    skor: float = Field(ge=0, le=1, description="probabilitas kelas terpilih")


app/model.pyPython
import joblib

from .skema import HasilSentimen


class PenganalisSentimen:
    def __init__(self, path: str):
        self.pipeline = joblib.load(path)  #+

    def prediksi(self, daftar_teks: list[str]) -> list[HasilSentimen]:
        proba = self.pipeline.predict_proba(daftar_teks)  #+
        kelas = self.pipeline.classes_
        hasil = []
        for p in proba:
            i = int(p.argmax())
            hasil.append(HasilSentimen(label=str(kelas[i]), skor=round(float(p[i]), 3)))  #+
        return hasil

def baca_csv(isi: str) -> np.ndarray:
    try:  #+

        return np.array([[float(b[k]) for k in KOLOM] for b in baris])
