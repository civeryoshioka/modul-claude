2. Anatomi Inferensi di PyTorch

Pada pelatihan, PyTorch mencatat semua operasi supaya bisa menghitung gradien mundur (backpropagation). Pada inferensi, pencatatan itu sia-sia: memboroskan memori dan waktu. Karena itu ada tiga kebiasaan wajib sebelum model menjawab request pertama. Bayangkan seorang koki yang menyiapkan mise en place: saat latihan ia mencatat setiap langkah untuk dievaluasi pelatihnya; saat restoran buka, ia hanya memasak.

model.eval()Mengubah perilaku lapisan yang berbeda antara pelatihan dan inferensi: BatchNorm memakai statistik tersimpan (bukan statistik batch), Dropout dimatikan. Lupa memanggilnya membuat hasil berubah-ubah tergantung isi batch.
torch.inference_mode()Mematikan pencatatan gradien (lebih agresif dari no_grad). Hemat memori dan lebih cepat. Tensor yang dihasilkannya tidak bisa dipakai lagi untuk pelatihan.
Bentuk, dtype, perangkatModel mengharapkan tensor dengan bentuk (N,C,H,W), dtype (float32), dan device (CPU/GPU) yang tepat. Tiga hal ini adalah sumber galat paling umum.

Model yang kita pakai

CNN angka sangat kecil, sengaja, agar semua bisa diikuti dan dilatih dalam hitungan detik. Arsitekturnya: satu lapisan konvolusi, ReLU, max-pooling, lalu satu lapisan linear ke 10 kelas.

model_cnn.pyPython
import torch
from torch import nn


class CNNAngka(nn.Module):
    def __init__(self):
        super().__init__()
        self.konv = nn.Conv2d(1, 8, kernel_size=3, padding=1)  #+
        self.pool = nn.MaxPool2d(2)  #+
        self.fc = nn.Linear(8 * 4 * 4, 10)  #+

    def forward(self, x):                    # x: (N, 1, 8, 8)
        x = self.pool(torch.relu(self.konv(x)))  #+
        return self.fc(x.flatten(1))         # logits (N, 10)  #+

def p50(fn, n=30):
    for _ in range(5):
        fn()
    t = []
    for _ in range(n):
        s = time.perf_counter(); fn(); t.append((time.perf_counter() - s) * 1000)
    return sorted(t)[n // 2]


def dengan_grad():
    m(x)


def tanpa_grad():
    with torch.inference_mode():  #+
        m(x)


print(f"waktu batch 8 (p50): dengan grad {p50(dengan_grad):.2f} ms | inference_mode {p50(tanpa_grad):.2f} ms")

3. Praproses, Pascaproses & Train–Serve Skew

Di notebook, praproses sering terasa seperti urusan sampingan: bagi dengan 255, resize, selesai. Pada layanan, praproses adalah bagian dari model. Bobot jaringan saraf dilatih untuk menerima angka dengan sebaran tertentu; kalau server memberinya angka dengan sebaran lain, hasilnya sampah, tanpa error apa pun. Para praktisi menyebutnya train–serve skew.

Analogi: sebuah resep kue yang ditakar dengan sendok ukur tertentu. Kalau dapur kedua memakai sendok yang ukurannya beda, resep yang sama menghasilkan kue yang berbeda, padahal "semua bahan sudah benar". Praproses adalah sendok ukur itu.

Satu sumber kebenaran

Aturan emas: fungsi praproses ditulis satu kali dan dipakai oleh pelatihan dan layanan. Jangan menulis ulang "yang kira-kira sama" di server. Inilah praprosesnya (mengubah matriks 8×8 bernilai 0–16 menjadi tensor yang dilihat model saat pelatihan):

praproses.pyPython
"""Praproses yang HARUS sama persis dengan saat pelatihan (satu sumber kebenaran)."""
import numpy as np

MEAN, STD = 0.305, 0.376      # dihitung dari data latih (lihat latih_cnn.py)  #+


def normalisasi(piksel_0_16: np.ndarray) -> np.ndarray:
    """Matriks 8x8 bernilai 0..16 -> tensor float32 (N,1,8,8) ternormalisasi."""
    x = np.asarray(piksel_0_16, dtype=np.float32).reshape(-1, 1, 8, 8) / 16.0  #+
    return ((x - MEAN) / STD).astype(np.float32)  #+

Konstanta MEAN dan STD adalah hasil perhitungan pada data latih (lihat keluaran latih_cnn.py di Bagian 2: mean=0.305 std=0.376). Konstanta ini adalah bagian dari model: kalau suatu hari model dilatih ulang, kedua angka itu bisa berubah, dan harus ikut berganti.

Pascaproses: dari logit ke jawaban

Keluaran mentah jaringan adalah logit: angka bebas yang belum berupa peluang. Untuk mengubahnya menjadi peluang kita memakai softmax. Dua hal penting dalam implementasi yang sudah kita pakai di inferensi.py:

inferensi.py (cuplikan)Python
def softmax(logit: np.ndarray) -> np.ndarray:
    e = np.exp(logit - logit.max(axis=1, keepdims=True))      # dikurangi max: stabil secara numerik  #+
    return e / e.sum(axis=1, keepdims=True)
  • Kurangi nilai maksimum sebelum exp. Secara matematis hasilnya sama, tetapi exp(1000) meluap menjadi inf sedangkan exp(1000 − 1000) aman. Ini disebut softmax yang stabil secara numerik.
  • Peluang dari softmax bukan keyakinan yang terkalibrasi. Jaringan saraf cenderung terlalu yakin: pada contoh angka 7 kita, probabilitasnya 1.0. Jangan menafsirkan "0,99" sebagai "99% pasti benar" tanpa kalibrasi. Beri ambang "tidak yakin" dan ukur dulu di data nyata.
  • Kembalikan top-k, bukan hanya argmax. Tiga kandidat teratas memberi klien bahan untuk menampilkan alternatif atau meminta konfirmasi.

5. Layanan PyTorch dengan FastAPI

Kini kita rakit semuanya. Karena nanti ingin membandingkan PyTorch dengan ONNX Runtime, kita pisahkan backend inferensi dari layanan web dengan antarmuka yang sama: logit = backend.jalankan(x). Layanan tidak perlu tahu mesin apa di belakangnya.

inferensi.pyPython
"""Dua backend dengan antarmuka yang sama: logit = backend.jalankan(x)."""
import numpy as np
import onnxruntime as ort
import torch

from model_cnn import CNNAngka


class BackendTorch:
    nama = "pytorch"

    def __init__(self, path="digit_cnn.pt"):
        self.model = CNNAngka()
        self.model.load_state_dict(torch.load(path, weights_only=True))   # aman: hanya memuat tensor  #+
        self.model.eval()                                                 # matikan dropout/batchnorm-train  #+

    def jalankan(self, x: np.ndarray) -> np.ndarray:
        with torch.inference_mode():                                      # tanpa pencatatan gradien  #+
            return self.model(torch.from_numpy(x)).numpy()


class BackendOnnx:
    nama = "onnxruntime"

    def __init__(self, path="digit_cnn.onnx", threads=1):
        opsi = ort.SessionOptions()
        opsi.intra_op_num_threads = threads  #+
        self.sesi = ort.InferenceSession(path, opsi, providers=["CPUExecutionProvider"])

    def jalankan(self, x: np.ndarray) -> np.ndarray:
        return self.sesi.run(None, {"gambar": x})[0]

    @asynccontextmanager
    async def lifespan(app: FastAPI):
        app.state.backend = BackendTorch() if backend == "torch" else BackendOnnx()  #+
        # warmup: jalankan sekali supaya request pertama pengguna tidak membayar biaya inisialisasi  #+
        app.state.backend.jalankan(np.zeros((1, 1, 8, 8), dtype=np.float32))  #+

        app.state.siap = False

        return response

            urut = np.argsort(-baris)[:3]
            hasil.append(Prediksi(
                angka=int(urut[0]), probabilitas=round(float(baris[urut[0]]), 4),
                top3=[Skor(angka=int(i), probabilitas=round(float(baris[i]), 4)) for i in urut],
                backend=nama, waktu_inferensi_ms=round(ms, 3)))
        return hasil

        return {"status": "ok"}

        return {"status": "ready", "backend": request.app.state.backend.nama}

            gambar = Image.open(berkas.file).convert("L")  #+

            raise HTTPException(status_code=415, detail="Berkas bukan gambar yang dikenali")  #+
        kecil = gambar.resize((8, 8), Image.Resampling.BOX)           # rata-ratakan blok piksel  #+

        t = time.perf_counter()

    @app.post("/prediksi/batch", response_model=list[Prediksi])

        t = time.perf_counter()
        logit = b.jalankan(x)
        return susun(logit, (time.perf_counter() - t) * 1000, b.nama)

    return app

6. Thread, Worker & Rebutan Inti CPU

Pada modul sebelumnya kita belajar bahwa def menjalankan inferensi di threadpool dan bahwa beberapa worker (proses) memanfaatkan beberapa inti CPU. Pada deep learning ada lapisan ketiga yang sering terlupa: thread di dalam satu operasi. Library numerik seperti PyTorch, NumPy (BLAS), dan ONNX Runtime membagi satu perkalian matriks besar ke beberapa thread (intra-op parallelism) secara otomatis.

Jadi satu request yang masuk ke satu worker sudah bisa memakai beberapa inti. Kalau kamu menyalakan 4 worker dan masing-masing membuka 4 thread di mesin 4 inti, terjadilah oversubscription: 16 thread berebut 4 inti, saling menyela, dan sering kali lebih lambat daripada konfigurasi yang lebih hemat. Analogi: empat koki (worker) di dapur dengan empat kompor, tetapi tiap koki membawa tiga asisten yang juga ingin memakai kompor yang sama. Dapurnya jadi sesak, bukan lebih cepat.

Percobaan nyata: kombinasi worker × thread

Untuk melihatnya, kita memakai jaringan besar (4,76 juta parameter) di balik sebuah endpoint yang membuat masukan acak di server, sehingga yang terukur hanyalah inferensi. Jumlah thread PyTorch per worker diatur lewat variabel lingkungan:

7. ONNX Runtime & Benchmark yang Jujur

ONNX (Open Neural Network Exchange) adalah format terbuka untuk menyimpan graf jaringan saraf. ONNX Runtime (ORT) adalah mesin yang menjalankannya dengan banyak optimasi (penggabungan operasi, pemilihan kernel, penjadwalan thread). Daya tariknya: model keluar dari ekosistem PyTorch, layanan tidak perlu memasang PyTorch (image lebih kecil dan startup lebih cepat), dan runtime yang sama bisa berjalan di CPU, GPU, dan perangkat lain. Analogi: PyTorch adalah dapur lengkap tempat resep dikembangkan; ONNX adalah resep tercetak yang bisa dimasak di dapur restoran mana pun dengan peralatan terbaiknya.

def ukur(fn, n, warm=20):
    for _ in range(warm):
        fn()
    t = []
    for _ in range(n):
        a = time.perf_counter(); fn(); t.append((time.perf_counter() - a) * 1000)  #+
    t.sort()
    return t[len(t) // 2], t[int(len(t) * 0.95) - 1]

def torch_fn(model, threads):
    def mk(x):
        torch.set_num_threads(threads)
        t = torch.from_numpy(x)

            with torch.inference_mode():  #+
                model(t)
        return f

8. Kuantisasi: Lebih Kecil, Belum Tentu Lebih Cepat

Bobot jaringan umumnya disimpan sebagai float32 (4 byte per angka). Kuantisasi menyimpan angka-angka itu dengan presisi lebih rendah, misalnya bilangan bulat 8-bit (int8, 1 byte). Analogi: menggambar peta dengan penggaris yang hanya punya 256 garis skala, bukan jutaan. Lebih hemat tempat, dengan kehilangan sedikit ketelitian. Harapan umum: model 4× lebih kecil, memori dan bandwidth lebih hemat, dan mungkin lebih cepat. Tanda tanya terakhir itu yang sering dilupakan.

Percobaan: kuantisasi dinamis int8 di ONNX Runtime

Pada perangkat keras dengan instruksi int8 khusus, atau pada model yang didominasi lapisan linear, hasilnya bisa sebaliknya. Karena itu: kuantisasi adalah hipotesis yang harus diuji pada perangkat keras target, bukan "tombol ajaib".

⚠️ Catatan tentang angka kecocokan keluaran Jaringan besar kita berbobot acak sehingga logitnya nyaris datar (rentang ≈ 0,04). Pada model itu, "kelas teratas sama pada 8/8 sampel" dan selisih logit 3e-06 hanyalah uji kewarasan, bukan bukti akurasi. Kualitas kuantisasi harus dinilai pada model terlatih dan data validasi, seperti pada CNN angka (akurasi tetap 0,980).

🧭 Kapan kuantisasi benar-benar membantu?
  • Model besar yang dibatasi memori/bandwidth (misalnya LLM di GPU): bobot 4-bit atau 8-bit memuat model yang tak akan muat dalam float16, dan memindahkan lebih sedikit data per token. Ini adalah alasan utama kuantisasi populer pada LLM (tidak diuji di sini: kami tak punya GPU).

  • Batasan ukuran berkas/memori (model di perangkat tepi, jumlah worker banyak).
  • Untuk keputusan serius: pertimbangkan static quantization dengan data kalibrasi dan quantization-aware training yang menjaga akurasi lebih baik, lalu ukur lagi akurasi dan latensi pada perangkat target.

Warmup: menghangatkan kompor sebelum restoran buka

Warmup berarti menjalankan model beberapa kali dengan masukan yang representatif sebelum menerima trafik sungguhan. Di layanan kita, itu ada di lifespan (layanan.py, baris 47–50). Beberapa praktik penting:

  • Gunakan bentuk masukan yang akan dipakai. Bila model menerima ukuran dinamis (panjang teks atau ukuran batch berbeda), hangatkan setiap bentuk umum, sebab kernel dan alokasi bergantung pada bentuk.
  • Jalankan beberapa kali, bukan sekali, terutama di GPU, dan tunggu sampai waktunya stabil.
  • Jangan terima trafik sebelum siap. Uvicorn tidak menerima koneksi sampai lifespan selesai startup, tetapi orkestrator tetap perlu tahu kapan replika boleh dialiri trafik, itulah fungsi /ready (503 sebelum siap, 200 sesudahnya).
  • Penalti sisa. Seperti terlihat di Bagian 5, request pertama di thread baru bisa sedikit lebih lambat walau sudah ada warmup. Pemanasan mengurangi, bukan menghapus, penalti itu.

10. Batching untuk Deep Learning

Konsep dynamic batching sudah kita bahas di modul sebelumnya, dengan model palsu berbiaya 20 ms + 1 ms per item. Sekarang kita buktikan pada jaringan saraf sungguhan. Kelas Pembatch yang kita pakai identik dengan versi sebelumnya (antrean asyncio, Future per request, run_in_executor, dan penerusan error); yang baru hanyalah fungsi model yang menumpuk masukan menjadi satu tensor:

batching_torch.pyPython
import asyncio
import time

import numpy as np
import torch

from model_besar import buat
from pembatch import Pembatch

model = buat()
torch.set_num_threads(4)


def fungsi_model(daftar):                          # daftar array (3,64,64) -> daftar logit (100,)
    x = torch.from_numpy(np.stack(daftar))         # (B,3,64,64): satu tensor untuk seluruh batch  #+
    with torch.inference_mode():
        return list(model(x).numpy())  #+


async def uji(maks_batch, n=128):
    pb = Pembatch(fungsi_model, maks_batch=maks_batch, maks_tunggu=0.005)
    pb.mulai()
    data = [np.random.RandomState(i).randn(3, 64, 64).astype(np.float32) for i in range(n)]
    lat = []

    async def satu(i):
        t = time.perf_counter()
        y = await pb.prediksi(data[i])
        lat.append((time.perf_counter() - t) * 1000)
        return y

    t0 = time.perf_counter()
    hasil = await asyncio.gather(*[satu(i) for i in range(n)])
    total = time.perf_counter() - t0
    await pb.berhenti()
    # kebenaran: hasil batch harus sama dengan inferensi satuan
    with torch.inference_mode():
        acuan = model(torch.from_numpy(data[7][None])).numpy()[0]
    sama = np.allclose(hasil[7], acuan, atol=1e-4)
    lat.sort()
    print(f"maks_batch={maks_batch:2d}  total {total*1000:6.0f} ms  throughput {n/total:6.0f} req/dtk  latensi rata2 {sum(lat)/n:6.0f} ms  p95 {lat[int(.95*n)-1]:6.0f} ms  hasil sama dgn satuan: {sama}")  #+


for mb in (1, 4, 16, 64):
    asyncio.run(uji(mb))

Memodelkan biaya batch dari data nyata

Dari hasil di atas kita bisa memperkirakan biaya satu panggilan model sebagai fungsi linear dari ukuran batch: biaya(b) ≈ a + c·b. Model sederhana ini cukup baik untuk memprediksi hasil di ukuran batch lain, dan kita pakai di Simulasi 8.

  • Memori membatasi ukuran batch. Aktivasi tumbuh linear dengan batch; di GPU, batch terlalu besar berujung out-of-memory. Tetapkan maks_batch dari perhitungan memori (Bagian 12), bukan hanya dari throughput.

11. Model Generatif: Decoding, Sampling & Streaming

Model klasifikasi menjawab dengan satu kali perhitungan. Model generatif (bahasa, kode, suara) bekerja berbeda: ia menghasilkan keluaran satu potongan (token) demi satu, dan setiap potongan baru bergantung pada semua potongan sebelumnya. Inilah yang disebut autoregressive decoding. Konsekuensinya sangat besar untuk cara menyajikannya, karena langkah-langkahnya tidak bisa dijalankan paralel: token ke-10 baru bisa dihitung setelah token ke-9 jadi.

Untuk memahaminya tanpa model raksasa, kita memakai model karakter mini: sebuah GRU (jaringan rekuren) berukuran 40.923 parameter yang belajar menebak karakter berikutnya dari korpus kecil berbahasa Indonesia. Prinsip decoding-nya sama dengan LLM, hanya skalanya jauh lebih kecil. Kode lengkapnya:

generatif.pyPython
import time

import torch
from torch import nn

from korpus import KORPUS

HURUF = sorted(set(KORPUS))
K2I = {c: i for i, c in enumerate(HURUF)}


class ModelKarakter(nn.Module):
    def __init__(self, vocab, dim=96):
        super().__init__()
        self.emb = nn.Embedding(vocab, 32)
        self.gru = nn.GRU(32, dim, batch_first=True)
        self.out = nn.Linear(dim, vocab)

    def forward(self, x, h=None):               # x: (N, T) indeks karakter
        y, h = self.gru(self.emb(x), h)  #+
        return self.out(y), h                   # logit (N, T, vocab), keadaan tersembunyi h  #+


def latih(langkah=1500, seed=0):
    torch.manual_seed(seed)
    data = torch.tensor([K2I[c] for c in KORPUS])
    m = ModelKarakter(len(HURUF))
    opt = torch.optim.Adam(m.parameters(), lr=0.01)
    T = 64
    for s in range(langkah):
        idx = torch.randint(0, len(data) - T - 1, (32,))
        x = torch.stack([data[i:i + T] for i in idx]); y = torch.stack([data[i + 1:i + T + 1] for i in idx])
        logit, _ = m(x)
        loss = nn.functional.cross_entropy(logit.reshape(-1, len(HURUF)), y.reshape(-1))
        opt.zero_grad(); loss.backward(); opt.step()
    return m, loss.item()


def pilih(logit, suhu=1.0, top_k=0, top_p=1.0):
    """Satu langkah sampling dari logit (V,) -> indeks."""
    logit = logit / max(suhu, 1e-6)  #+
    p = torch.softmax(logit, -1)
    if top_k > 0:
        v, _ = torch.topk(p, top_k); p = torch.where(p < v[-1], torch.zeros_like(p), p)  #+
    if top_p < 1.0:
        urut, idx = torch.sort(p, descending=True)
        kum = torch.cumsum(urut, 0)
        buang = kum - urut > top_p
        urut[buang] = 0; p = torch.zeros_like(p).scatter(0, idx, urut)  #+
    return torch.multinomial(p / p.sum(), 1).item()  #+


@torch.inference_mode()
def hasilkan(m, awal, n, suhu=0.8, top_k=0, top_p=1.0, pakai_cache=True, seed=0):
    """Generator karakter. pakai_cache=True: bawa keadaan h. False: hitung ulang seluruh konteks tiap langkah."""
    torch.manual_seed(seed)
    ids = [K2I[c] for c in awal]
    logit, h = m(torch.tensor([ids]))  #+
    for _ in range(n):
        i = pilih(logit[0, -1], suhu, top_k, top_p)
        ids.append(i)
        yield HURUF[i]
        if pakai_cache:
            logit, h = m(torch.tensor([[i]]), h)                 # hanya 1 token baru  #+
        else:
            logit, _ = m(torch.tensor([ids]))                    # ulang SELURUH konteks  #+


if __name__ == "__main__":
    t = time.perf_counter()
    m, loss = latih()
    print(f"latih selesai: loss akhir {loss:.3f} | {len(HURUF)} karakter unik | {sum(p.numel() for p in m.parameters())} parameter | {time.perf_counter()-t:.1f} dtk")
    torch.save(m.state_dict(), "gen.pt")
    for suhu in (0.3, 0.8, 1.5):
        print(f"suhu {suhu}: " + "".join(hasilkan(m, "model ", 90, suhu=suhu, top_k=0)))

Streaming token lewat FastAPI

Sekarang kita sajikan generator itu sebagai layanan, memakai Server-Sent Events seperti di modul sebelumnya. Ada satu hal baru: karena tiap langkah decode adalah komputasi yang memblokir, kita menjalankannya lewat asyncio.to_thread supaya event loop tetap bebas melayani klien lain di antara token. import asyncio
from contextlib import asynccontextmanager

import torch
from fastapi import FastAPI
from fastapi.responses import EventSourceResponse
from pydantic import BaseModel, Field

from generatif import HURUF, K2I, ModelKarakter, pilih

torch.set_num_threads(1)


class Permintaan(BaseModel):
    awal: str = Field(default="model ", min_length=1, max_length=60)  #+
    maks_token: int = Field(default=80, ge=1, le=300)  #+
    suhu: float = Field(default=0.8, gt=0, le=2)  #+
    top_k: int = Field(default=0, ge=0, le=27)  #+
    top_p: float = Field(default=1.0, gt=0, le=1)  #+


@asynccontextmanager
async def lifespan(app: FastAPI):
    m = ModelKarakter(len(HURUF)); m.load_state_dict(torch.load("gen.pt", weights_only=True)); m.eval()
    app.state.model = m
    yield


app = FastAPI(lifespan=lifespan)


def satu_langkah(m, ids_atau_i, h, p):
    with torch.inference_mode():
        logit, h = m(ids_atau_i, h)  #+
        return pilih(logit[0, -1], p.suhu, p.top_k, p.top_p), h


@app.post("/hasilkan", response_class=EventSourceResponse)
async def hasilkan_stream(p: Permintaan):
    m = app.state.model
    tak_dikenal = [c for c in p.awal if c not in K2I]
    if tak_dikenal:
        yield {"galat": f"karakter tidak dikenal: {sorted(set(tak_dikenal))}"}
        return
    x, h = torch.tensor([[K2I[c] for c in p.awal]]), None
    for _ in range(p.maks_token):
        # satu langkah = komputasi yang memblokir -> lempar ke thread agar event loop tetap bebas
        i, h = await asyncio.to_thread(satu_langkah, m, x, h, p)  #+
        x = torch.tensor([[i]])  #+
        yield {"token": HURUF[i]}  #+

12. GPU & Perencanaan Memori

ℹ️ Status pengujian bagian ini Lingkungan penyusunan modul ini tidak memiliki GPU (torch.cuda.is_available() bernilai False). Karena itu kode GPU di bawah adalah pola yang tidak dijalankan, dan Simulasi 11 adalah perhitungan rumus (bukan pengukuran). Gunakan keduanya sebagai titik awal, lalu ukur pada perangkat kerasmu.

GPU unggul pada operasi matriks besar yang paralel, tetapi mengubah banyak hal pada layanan: ia punya memori sendiri (VRAM) yang terbatas, perpindahan data CPU↔GPU berbiaya, dan operasinya berjalan asinkron. Berikut pola dasarnya.

pola_gpu.py (pola; tidak dijalankan: tidak ada GPU)Python
import torch

device = torch.device("cuda" if torch.cuda.is_available() else "cpu")

model = CNNAngka()
model.load_state_dict(torch.load("digit_cnn.pt", weights_only=True, map_location=device))   # petakan bobot langsung ke perangkat
model.to(device).eval()                          # pindahkan SEKALI saat startup, bukan per request

@torch.inference_mode()
def jalankan(x_np):
    x = torch.from_numpy(x_np).to(device, non_blocking=True)   # CPU -> GPU: salinan berbiaya
    with torch.autocast(device_type=device.type, dtype=torch.float16, enabled=(device.type == "cuda")):
        logit = model(x)                         # presisi campuran: lebih cepat & hemat memori di GPU
    return logit.float().cpu().numpy()           # GPU -> CPU: memaksa menunggu hasil siap

# MENGUKUR WAKTU DI GPU: operasi CUDA berjalan asinkron, jadi panggil ini sebelum membaca jam
torch.cuda.synchronize()

Salinan antar-perangkat berbiayaKumpulkan data menjadi satu tensor besar (batching) lalu salin sekali, bukan banyak salinan kecil.

Konkurensi di GPU: satu proses per GPU

  • Satu proses per GPU adalah pola yang paling umum untuk layanan sederhana. Beberapa worker pada GPU yang sama masing-masing memuat salinan model dan membawa overhead konteks CUDA sendiri (beberapa ratus MB per proses), sehingga memori terbuang tanpa menambah kecepatan berarti.
  • Proses yang di-fork setelah CUDA diinisialisasi umumnya bermasalah; inisialisasi CUDA sebaiknya terjadi di dalam tiap worker (misalnya di lifespan), bukan di proses induk.
  • Karena GPU sudah memproses ribuan operasi paralel, batching (Bagian 10) adalah cara utama memanfaatkannya, bukan menambah thread.

Berapa memori yang dibutuhkan?

Pertanyaan pertama sebelum menyewa GPU: apakah modelnya muat? Memori VRAM dipakai oleh tiga hal utama:

KomponenRumus perkiraanCatatan
Bobotjumlah parameter × byte per parameterfloat32 = 4 B, float16/bfloat16 = 2 B, int8 = 1 B, 4-bit = 0,5 B
KV cache (model bahasa transformer)2 × lapisan × (head KV × dim head) × panjang konteks × batch × byteTumbuh dengan konteks dan jumlah pengguna serentak; sering jadi pembatas utama
Aktivasi & bufferBergantung model dan ukuran batchKita pakai perkiraan kasar: ± 10% dari bobot + 1 GB

Contoh: model 7 miliar parameter dalam float16 butuh 7 × 109 × 2 B = 14 GB hanya untuk bobot. Dengan 32 lapisan, dimensi 4096, dan semua head menyimpan KV, tiap token menambah 2 × 32 × 4096 × 2 B = 0,5 MB cache, jadi satu percakapan 4.096 token memakai ± 2 GB. Sepuluh percakapan serentak berarti 20 GB cache, lebih besar daripada model itu sendiri.

Layanan yang tak bisa diamati adalah layanan yang pasti akan mengejutkanmu. Pada deep learning ada dua kelompok hal yang perlu dipantau: kesehatan sistem (cepat, tersedia, tidak error) dan kesehatan model (masih menjawab dengan baik pada data yang sebenarnya masuk).

Metrik sistem

Kita punya penghitung dan histogram latensi sederhana gaya Prometheus (tanpa library tambahan), dipasang lewat middleware di layanan.py:

metrik.pyPython
import bisect
import threading

BATAS_MS = [1, 2, 5, 10, 25, 50, 100, 250, 1000]  #+


class Metrik:
    """Penghitung & histogram latensi bergaya Prometheus (tanpa library tambahan)."""

    def __init__(self):
        self.kunci = threading.Lock()
        self.jumlah: dict[tuple[str, int], int] = {}
        self.bucket = [0] * (len(BATAS_MS) + 1)
        self.total_ms = 0.0

    def catat(self, path: str, status: int, ms: float):  #+
        with self.kunci:  #+
            self.jumlah[(path, status)] = self.jumlah.get((path, status), 0) + 1  #+
            self.bucket[bisect.bisect_left(BATAS_MS, ms)] += 1  #+
            self.total_ms += ms  #+

    def teks(self) -> str:
        with self.kunci:
            baris = ["# TYPE permintaan_total counter"]
            for (path, status), n in sorted(self.jumlah.items()):
                baris.append(f'permintaan_total{{path="{path}",status="{status}"}} {n}')
            baris.append("# TYPE latensi_ms histogram")
            kumulatif = 0
            for batas, n in zip(BATAS_MS, self.bucket):
                kumulatif += n
                baris.append(f'latensi_ms_bucket{{le="{batas}"}} {kumulatif}')
            kumulatif += self.bucket[-1]
            baris.append(f'latensi_ms_bucket{{le="+Inf"}} {kumulatif}')
            baris.append(f"latensi_ms_sum {self.total_ms:.3f}")
            baris.append(f"latensi_ms_count {kumulatif}")
            return "\n".join(baris) + "\n"

Kesehatan model: drift

Model dilatih pada data masa lalu. Dunia berubah: kamera baru dengan pencahayaan berbeda, musim yang mengubah foto, bahasa gaul baru. Saat sebaran data masuk bergeser dari sebaran data latih, kualitas model turun, tanpa error apa pun dan tanpa label sebenarnya untuk memeriksanya. Itulah data drift. Kabar baiknya: sebaran input bisa dipantau tanpa label.

Ukuran yang populer adalah PSI (Population Stability Index): bagi nilai fitur ke dalam bin, bandingkan proporsi tiap bin antara data acuan (latih) dan data hidup:

PSI = Σ (hidupi − acuani) × ln(hidupi / acuani)

Patokan umum di industri (kaidah praktis, bukan hukum): PSI < 0,1 stabil; 0,1–0,25 pergeseran sedang, perlu dicermati; > 0,25 pergeseran besar, selidiki atau latih ulang.

  • Selidiki dulu: apakah sumber data berubah (perangkat, format, praproses di hulu)? Banyak "drift" ternyata bug praproses (Bagian 3).

  • Latih ulang dengan data baru, lalu rilis bertahap: shadow (model baru menjawab diam-diam, dibandingkan), lalu canary (sebagian kecil trafik), baru penuh.
  • Pantau juga sebaran keluaran: bila proporsi kelas atau histogram keyakinan berubah drastis tanpa sebab bisnis, itu sinyal tambahan.

Garis hijau adalah kapasitas (replika yang sudah siap × kapasitas per replika), garis oranye trafik, area merah adalah antrean yang menumpuk. Model fluida sederhana (per detik), bukan pengukuran.

FastAPI sangat baik sebagai pintu depan dan untuk model kecil sampai menengah. Tetapi bila kebutuhanmu tumbuh, alat khusus menyediakan fitur yang kita bangun sendiri dengan susah payah di modul ini (dan kadang tidak mungkin kita samai):

import io

from fastapi import HTTPException
from PIL import Image, ImageOps, UnidentifiedImageError

MAKS_SISI = 4096


def buka_gambar_aman(file):
    """Buka gambar dari unggahan: tolak yang rusak/terlalu besar, luruskan orientasi EXIF, ratakan alfa."""
    try:
        g = Image.open(file)
        g.load()
    except (UnidentifiedImageError, OSError):  #+
        raise HTTPException(status_code=415, detail="Berkas bukan gambar yang dikenali")
    if max(g.size) > MAKS_SISI:  #+
        raise HTTPException(status_code=413, detail=f"Sisi gambar maksimal {MAKS_SISI} piksel")
    g = ImageOps.exif_transpose(g)                      # foto ponsel yang terputar diluruskan  #+
    if g.mode in ("RGBA", "LA"):                        # PNG transparan: tempel di atas latar putih  #+
        latar = Image.new("RGB", g.size, (255, 255, 255))  #+
        latar.paste(g, mask=g.getchannel("A")); g = latar  #+
    return g.convert("L")  #+


if __name__ == "__main__":

Latihan 3 · Hitung PSI di server Tulis fungsi psi(acuan, hidup) dengan 8 bin intensitas piksel (lebar 2, rentang 0–16). Uji dengan menipiskan "tinta" (mengalikan piksel dengan kontras 1,0 → 0,3) pada 100 contoh. Tabelkan PSI dan akurasi. Apa yang kamu simpulkan tentang PSI sebagai alarm?
Lihat solusi Latihan 3
latihan3.pyPython
import json

import numpy as np

import praproses
from inferensi import BackendTorch

EPS = 1e-4
TEPI = np.linspace(0, 16.0001, 9)           # 8 bin intensitas piksel (lebar 2)


def psi(acuan, hidup):  #+
    a = np.histogram(acuan, bins=TEPI)[0] / acuan.size + EPS  #+
    h = np.histogram(hidup, bins=TEPI)[0] / hidup.size + EPS  #+
    return float(np.sum((h - a) * np.log(h / a)))  #+


X, Y = np.load("contoh_uji.npy")[:100], np.load("label_uji.npy")[:100]
model = BackendTorch()
print(f"{'kontras tinta':>13s} | {'PSI':>6s} | {'akurasi (butuh label)':>22s}")
hasil = {}
for k in (1.0, 0.8, 0.6, 0.4, 0.3):
    hidup = np.clip(X * k, 0, 16)  #+
    akurasi = (model.jalankan(praproses.normalisasi(hidup)).argmax(1) == Y).mean()
    hasil[str(k)] = {"psi": round(psi(X, hidup), 4), "akurasi": float(akurasi)}
    print(f"{k:13.1f} | {psi(X, hidup):6.3f} | {akurasi:22.2f}")
json.dump(hasil, open("psi_ref.json", "w"))

Perhatikan jarak antara alarm dan kerusakan: pada kontras 0,8, PSI sudah 0,96 (jauh di atas ambang 0,25) padahal akurasi baru turun dari 0,96 ke 0,95. Akurasi baru turun tajam di bawah kontras 0,5 (0,76 pada kontras 0,4; 0,49 pada 0,3). PSI adalah indikator dini yang sensitif: ia mendeteksi bahwa data berubah, bukan bahwa model sudah rusak. Perlakukan sebagai pemicu investigasi (apakah sumber data berubah? bagaimana akurasi pada sampel berlabel?), bukan pemicu otomatis untuk melatih ulang.
