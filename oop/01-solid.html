Memahami SOLID dari Nol

Lima prinsip desain OOP yang sering dihafal tapi jarang dipahami, dijelaskan lewat analogi dapur restoran, diagram, simulasi interaktif, dan kode Java yang sudah dikompilasi dan dijalankan. Estimasi waktu belajar ± 3 jam.

🎯 Tujuan belajar Setelah modul ini kamu bisa menjelaskan masalah apa yang diselesaikan oleh masing-masing prinsip SOLID (bukan sekadar menyebut kepanjangannya), mengenali bau kode yang menandakan sebuah prinsip dilanggar, memperbaikinya dengan Java, menjelaskan kenapa kelimanya saling melengkapi, dan yang tidak kalah penting, tahu kapan tidak perlu menerapkannya.
Prasyarat: paham dasar Java (kelas, objek, method, interface, extends/implements). Semua kode memakai Java 17 atau lebih baru; kalau kamu memakai Java 8/11, ganti record dengan kelas biasa.

1. Kenapa SOLID Terasa Membingungkan?

Hampir semua orang yang belajar OOP pernah berhenti di lima huruf ini. Kamu tidak sendirian, dan penyebabnya jarang karena kamu kurang paham OOP. SOLID hanya kebetulan sering diajarkan dengan cara yang paling menyulitkan:

1 · Definisinya terlalu abstrak"Sebuah kelas harus punya satu, dan hanya satu, alasan untuk berubah." Tapi alasan itu apa? Siapa yang menentukan? Kalimatnya benar, namun tidak memberi pegangan untuk menulis kode besok pagi.
2 · Contohnya terlalu kecilKode 10 baris dipecah menjadi 6 kelas dan 3 interface. Wajar kalau kamu bertanya, "Ini bukannya malah ribet?" Manfaat SOLID baru terasa di proyek yang besar, berumur panjang, dan terus berubah.
3 · Diajarkan sebagai hukum, bukan obatResep tanpa tahu penyakitnya hanya jadi hafalan. Setiap prinsip lahir dari rasa sakit tertentu (kode rapuh, kaku, sulit diuji). Kenali sakitnya dulu, barulah obatnya masuk akal.
4 · Kelimanya saling tumpang tindihSatu kode buruk sering melanggar dua atau tiga prinsip sekaligus, sehingga sulit memilah "ini pelanggaran yang mana?". Di Bagian 10 kita lihat bagaimana kelimanya saling mengunci.

Karena itu modul ini memakai urutan yang berbeda untuk setiap prinsip. Kita mulai dari rasa sakitnya, bukan dari definisinya:

  1. Analogi dulu. Kita pahami idenya lewat kehidupan sehari-hari (dapur restoran), tanpa satu baris kode pun.
  2. Kode yang menyakitkan. Contoh Java yang berjalan benar hari ini tetapi menyimpan masalah untuk besok. Baris bermasalah diberi garis merah.
  3. Perubahan datang. Lewat simulasi kamu sendiri yang menekan tombol "bos minta fitur baru" dan melihat kerusakan yang terjadi.
  4. Kode yang sudah diobati. Versi baru dengan garis hijau di bagian kunci, lengkap dengan keluaran program yang sungguhan dijalankan.
  5. Kapan jangan memakainya. Setiap prinsip punya sisi gelap bila dipakai berlebihan, dan kita bahas itu dengan jujur.
📜 Sedikit sejarah Gagasan-gagasannya lebih tua daripada namanya. Bertrand Meyer merumuskan Open/Closed Principle pada 1988, Barbara Liskov memperkenalkan konsep substitusi subtipe pada 1987 (dibuat formal bersama Jeannette Wing pada 1994), lalu Robert C. Martin ("Uncle Bob") merangkum prinsip-prinsip desain pada awal 2000-an. Singkatan SOLID sendiri dikaitkan dengan Michael Feathers. Jadi SOLID bukan hukum alam, melainkan pengalaman puluhan tahun programmer yang sudah merasakan sakitnya proyek yang membusuk.

2. Bau Kode: Penyakit yang Diobati SOLID

Perangkat lunak jarang rusak dalam semalam. Ia membusuk pelan-pelan: tiap permintaan fitur ditambal dengan cara tercepat, hingga suatu hari menambah satu tombol kecil memakan waktu seminggu. Robert C. Martin menggambarkan pembusukan desain lewat empat gejala. Kenali keempatnya, karena setiap prinsip SOLID adalah obat untuk satu atau lebih dari mereka.

🧱Rigidity (kaku)Satu perubahan kecil memaksa banyak bagian lain ikut diubah. Seperti memindahkan stopkontak di rumah yang dindingnya beton: bobol dulu temboknya. Estimasi "cuma 1 jam" selalu meleset.
🃏Fragility (rapuh)Mengubah bagian A merusak bagian B yang tampak tak berhubungan. Seperti menara kartu: mengganti satu kartu di bawah meruntuhkan lantai atas. Programmer jadi takut menyentuh kode.
🛋️Immobility (tak bisa dipindah)Bagian yang berguna tidak bisa dipakai di tempat lain karena terlalu terjalin dengan konteksnya. Seperti sofa yang dibaut ke lantai: bagus, tetapi tak bisa dibawa ke rumah baru.
🍯Viscosity (kental)Cara yang benar lebih susah daripada cara yang kotor, sehingga orang memilih menambal. Seperti jalan pintas di taman: makin sering dilewati, makin rusak rumputnya.

Dua ukuran: coupling dan cohesion

Kalau keempat gejala itu adalah demamnya, maka dua istilah berikut adalah suhu badan yang bisa kamu ukur. Hampir seluruh SOLID dapat dibaca sebagai usaha menurunkan coupling dan menaikkan cohesion.

Coupling (keterikatan antar kelas)Seberapa banyak sebuah kelas "tahu" dan "bergantung" pada kelas lain. Makin ketat, makin besar efek riaknya saat ada yang berubah. Targetnya rendah. Bayangkan kabel antar-perangkat: semakin sedikit yang tersambung permanen, semakin mudah mencabut dan mengganti.
Cohesion (kekompakan isi kelas)Seberapa erat anggota di dalam satu kelas mengerjakan satu tujuan yang sama. Targetnya tinggi. Bayangkan laci peralatan: laci "sendok-garpu" kompak, laci "serba ada" berisi baterai bekas, kunci, dan sendok.

3. Bekal OOP Sebelum Mulai

SOLID memakai empat konsep OOP sebagai bahan bakunya. Kalau salah satunya masih goyah, SOLID akan terasa seperti teka-teki. Mari kita rapikan dulu, sambil membaca contoh kecil yang akan terus muncul.

Abstraksi (interface)Kontrak yang menyatakan apa yang bisa dilakukan tanpa menyebut bagaimana. Seperti tombol "kirim" pada aplikasi pesan: kamu tak peduli lewat jalur apa pesan terkirim.
PolimorfismeKode yang sama bisa bekerja dengan banyak jenis objek, selama semuanya memenuhi kontrak. Yang dijalankan adalah versi milik objek aslinya saat program berjalan.
EnkapsulasiData dan perilaku disatukan, dan isi dalam disembunyikan di balik method. Orang luar cukup tahu tombolnya, bukan kabelnya.
Komposisi ("has-a")Sebuah objek memiliki objek lain sebagai bagiannya, alih-alih menjadi turunannya (is-a). Komposisi lebih lentur karena bagian bisa diganti saat program berjalan.
Main.java · abstraksi, polimorfisme, komposisiJava 17+
// Kontrak (abstraksi): APA yang bisa dilakukan
interface Notifier {
    void send(String message);
}

// Implementasi (detail): BAGAIMANA melakukannya
class EmailNotifier implements Notifier {
    public void send(String message) { System.out.println("Email -> " + message); }
}

class SmsNotifier implements Notifier {
    public void send(String message) { System.out.println("SMS   -> " + message); }
}

// Komposisi ("has-a"): AlertService PUNYA sebuah Notifier, tanpa tahu jenisnya
class AlertService {
    private final Notifier notifier;

    AlertService(Notifier notifier) {
        this.notifier = notifier;
    }

    void alert(String message) {
        notifier.send("[ALERT] " + message);   // polimorfisme: yang dipanggil versi milik objek aslinya
    }
}

public class Main {
    public static void main(String[] args) {
        new AlertService(new EmailNotifier()).alert("Server mati");
        new AlertService(new SmsNotifier()).alert("Server mati");
    }
}
Keluaran (dijalankan dengan JDK 21)
Email -> [ALERT] Server mati
SMS   -> [ALERT] Server mati

AlertService tidak tahu apakah ia mengirim email atau SMS. Ia hanya tahu ada Notifier yang bisa send. Kemampuan "tidak perlu tahu" inilah yang akan kita pakai berkali-kali. Perhatikan juga garis pemisahnya: interface adalah apa, kelas implementasi adalah bagaimana. Hampir semua perbaikan di modul ini adalah menaruh sebuah interface di antara dua kelas.

4. Peta SOLID dalam Satu Dapur

Sebelum menyelam ke kode, kita pakai satu analogi yang sama untuk kelima prinsip: sebuah warung makan, "Warung Bu Siti". Kodemu ibarat cara warung itu diorganisasi, dan permintaan fitur baru ibarat perubahan di warung (menu baru, mesin kasir baru, supplier baru).

SSatu orang, satu peranAwalnya Bu Siti sendirian merangkap koki, kasir, pelayan, dan tukang cuci. Setiap perubahan (resep baru, mesin kasir baru, aturan kebersihan baru) mengganggu orang yang sama dan pekerjaannya saling mengacau. Solusi: pisahkan peran, dan setiap peran punya satu pihak yang berhak meminta perubahannya.
OMenu baru = kartu baruMenu ditulis di kartu resep terpisah dalam sebuah rak. Menu baru berarti menaruh kartu baru; dapur tidak dibongkar dan resep lama tidak disentuh (jadi tidak mungkin ikut rusak). Dapurnya terbuka untuk perluasan, tertutup untuk pembongkaran.
LKoki penggantiSaat koki utama libur, koki pengganti harus mampu mengerjakan semua yang dijanjikan koki utama. Pelayan tak perlu tahu siapa yang masak. Kalau pengganti ternyata "tidak bisa menggoreng", pelayan yang sudah menerima pesanan goreng akan celaka.
IKartu tugas per peranBukan satu buku panduan 300 halaman untuk semua orang. Tukang cuci menerima kartu "cuci piring", kasir menerima kartu "cara memakai mesin". Tak ada yang dipaksa menandatangani tugas yang tak ia kerjakan.
DTiket pesanan standarPelayan menempel tiket di rel, bukan berteriak "Pak Joko di kompor kiri!". Koki mana pun bisa membaca tiket yang sama. Pelayan (pembuat kebijakan) dan koki (pelaksana) sama-sama bergantung pada format tiket, bukan satu sama lain.
🎯 Benang merahnyaKelima prinsip bertanya hal yang sama dari sudut berbeda: "Kalau sesuatu berubah, seberapa kecil area yang harus kusentuh, dan seberapa yakin aku bahwa yang lain tidak rusak?"

S5. Single Responsibility Principle (SRP)

📌 Definisi Sebuah kelas (atau modul) harus punya satu, dan hanya satu, alasan untuk berubah. Robert C. Martin kemudian mempertajamnya: kelas itu hanya bertanggung jawab kepada satu aktor, yaitu satu kelompok orang atau bagian organisasi yang berhak meminta perubahan.

Analogi. Kembali ke Warung Bu Siti. Kalau Bu Siti sendirian merangkap koki, kasir, dan tukang cuci, maka resep baru dari pelanggan, mesin kasir baru dari bank, dan aturan kebersihan dari dinas kesehatan, semuanya jatuh ke orang yang sama. Akibatnya bukan hanya capek: saat ia sibuk mengganti struk kasir, ia lupa mematikan kompor. Perubahan di satu peran menyenggol peran lain karena mereka berbagi tangan, alat, dan kepala yang sama. Solusinya bukan "setiap orang mengerjakan satu gerakan", melainkan "setiap peran punya satu atasan yang berhak mengubahnya".

⚠️ Salah kaprah paling umum SRP bukan "satu kelas hanya boleh punya satu method" dan bukan "satu kelas hanya melakukan satu hal kecil". Sebuah kelas PayCalculator boleh punya sepuluh method asalkan semuanya melayani satu kepentingan yang sama: kebijakan penggajian. Pertanyaannya bukan "berapa banyak yang ia lakukan?", melainkan "berapa banyak pihak berbeda yang bisa memaksanya berubah?"

Kode yang menyakitkan

Ini contoh klasik dari Uncle Bob: kelas Employee yang melayani tiga aktor sekaligus. Keuangan menghitung gaji, HR membuat laporan jam kerja resmi, dan tim IT mengurus penyimpanan. Kodenya tampak rapi dan berjalan benar hari ini.

Main.java · Employee melayani tiga aktorJava 17+
class Employee {
    private final String name;
    private final int hoursWorked;
    private final double hourlyRate;

    Employee(String name, int hoursWorked, double hourlyRate) {
        this.name = name;
        this.hoursWorked = hoursWorked;
        this.hourlyRate = hourlyRate;
    }

    // Dipakai bersama oleh Keuangan DAN Kepegawaian (HR)
    int regularHours() {  //!
        return Math.min(hoursWorked, 40);
    }

    // Aktor 1: bagian Keuangan (kebijakan gaji & lembur)
    double calculatePay() {
        int overtime = hoursWorked - regularHours();
        return regularHours() * hourlyRate + overtime * hourlyRate * 1.5;
    }

    // Aktor 2: bagian Kepegawaian/HR (laporan jam kerja resmi)
    String reportHours() {
        return name + ": " + regularHours() + " jam reguler, "
                + (hoursWorked - regularHours()) + " jam lembur";
    }

    // Aktor 3: tim IT/DBA (cara data disimpan)
    void save() {
        System.out.println("INSERT INTO employee VALUES ('" + name + "', ...)");
    }
}

public class Main {
    public static void main(String[] args) {
        Employee budi = new Employee("Budi", 45, 50_000);
        System.out.println("Gaji   : Rp" + (long) budi.calculatePay());
        System.out.println("Laporan: " + budi.reportHours());
        budi.save();
    }
}

Kode yang sudah diobati

Kita pecah menurut aktor, bukan menurut jumlah method. Data (Employee) dipisah dari tiga kebijakan, masing-masing hanya punya satu pihak yang berhak mengubahnya.

Main.java · satu kelas, satu majikanJava 17+
// 1) Hanya data
record Employee(String name, int hoursWorked, double hourlyRate) { }

// 2) Alasan berubah: kebijakan penggajian (Keuangan)
class PayCalculator {  //+
    double calculate(Employee e) {
        int regular = Math.min(e.hoursWorked(), 40);
        int overtime = e.hoursWorked() - regular;
        return regular * e.hourlyRate() + overtime * e.hourlyRate() * 1.5;
    }
}

// 3) Alasan berubah: format laporan resmi (HR)
class HourReporter {  //+
    String report(Employee e) {
        int regular = Math.min(e.hoursWorked(), 40);
        int overtime = e.hoursWorked() - regular;
        return e.name() + ": " + regular + " jam reguler, " + overtime + " jam lembur";
    }
}

// 4) Alasan berubah: cara penyimpanan (IT/DBA)
class EmployeeRepository {  //+
    void save(Employee e) {
        System.out.println("INSERT INTO employee VALUES ('" + e.name() + "', ...)");
    }
}

public class Main {
    public static void main(String[] args) {
        Employee budi = new Employee("Budi", 45, 50_000);
        System.out.println("Gaji   : Rp" + (long) new PayCalculator().calculate(budi));
        System.out.println("Laporan: " + new HourReporter().report(budi));
        new EmployeeRepository().save(budi);
    }
}

💡 "Tapi angka 40 sekarang muncul dua kali. Bukankah itu melanggar DRY?" Tidak. Don't Repeat Yourself berlaku untuk pengetahuan yang sama, bukan untuk teks yang kebetulan mirip. "Batas lembur gaji" dan "batas jam reguler menurut hukum" saat ini bernilai sama, tetapi keduanya adalah dua pengetahuan berbeda yang bisa berpisah kapan saja, dan hari itu sudah kita saksikan di simulasi. Menyatukannya demi menghindari duplikasi justru membuat kopling tersembunyi antar aktor.

Cara mendeteksi pelanggaran SRP

  • Nama kabur: Manager, Helper, Util, Processor, atau nama yang memakai kata "dan" (UserValidatorAndSaver).
  • Import dari banyak lapisan: satu file mengimpor kelas UI, JDBC, HTTP, dan format PDF sekaligus.
  • Kohesi rendah: kelompok method yang memakai field berbeda; kamu bisa "memotong" kelas menjadi dua tanpa ada garis yang putus.
  • Konflik merge berulang: dua orang dari tim berbeda sering mengedit file yang sama untuk alasan yang tidak berhubungan.
  • Tes sulit disiapkan: untuk menguji perhitungan gaji kamu harus menyiapkan database dan printer.

Jebakan

  • Memecah berlebihan. Kelas dengan satu method bernama execute() untuk setiap langkah kecil membuat pembaca melompat-lompat di 30 file. Pecah hanya sepanjang ada aktor yang berbeda atau laju perubahan yang berbeda.
  • Memecah sebelum ada aktor kedua. Jika hanya ada satu pihak yang pernah meminta perubahan, belum ada alasan memisah. Pisahkan ketika perubahan kedua yang berbeda sumbernya benar-benar muncul.
  • Lupa pengkoordinasi. Setelah dipecah, harus ada kelas tipis yang merangkai alur (seperti CheckoutService di Bagian 11). Itu tidak melanggar SRP: tugasnya satu, yaitu mengatur urutan.
✅ Intisari S Kelompokkan hal-hal yang berubah karena alasan yang sama, dan pisahkan hal-hal yang berubah karena alasan berbeda. Ukurannya bukan jumlah method, melainkan jumlah majikan.

O6. Open/Closed Principle (OCP)

📌 Definisi Entitas perangkat lunak (kelas, modul, fungsi) harus terbuka untuk perluasan, tetapi tertutup untuk modifikasi (Bertrand Meyer, 1988). Dalam bahasa praktis: perilaku baru ditambahkan dengan menulis kode baru, bukan dengan membongkar kode lama yang sudah berjalan dan teruji.

Analogi. Ponselmu bisa memasang aplikasi baru kapan saja tanpa pabrik harus membongkar sistem operasinya. Sistem operasi "tertutup" (tak diubah saat kamu memasang aplikasi) tetapi "terbuka" (menerima aplikasi apa saja yang mengikuti aturan mainnya). Di Warung Bu Siti, menu baru adalah kartu resep baru di rak, bukan merombak seluruh dapur.

Kode yang sudah diobati: Strategy


Kita memperkenalkan sebuah titik variasi: interface DiscountPolicy. Setiap aturan diskon menjadi kelas kecil. Kelas Checkout hanya bicara dengan interface itu, jadi ia tertutup terhadap jenis diskon baru. Perhatikan VipDiscount: seluruh fitur baru berupa satu kelas tambahan.


Main.java · diskon sebagai strategiJava 17+
import java.util.List;

// Abstraksi yang stabil
interface DiscountPolicy {
    double discount(double total);
}

// Setiap aturan = satu kelas kecil
class NoDiscount implements DiscountPolicy {
    public double discount(double total) { return 0; }
}

class MemberDiscount implements DiscountPolicy {
    public double discount(double total) { return total * 0.05; }
}

class StudentDiscount implements DiscountPolicy {
    public double discount(double total) { return total * 0.10; }
}

// Kebutuhan baru: cukup MENAMBAH kelas. Tidak ada kelas lama yang diubah.
class VipDiscount implements DiscountPolicy {  //+
    public double discount(double total) {
        return Math.min(total * 0.15, 50_000);   // 15%, maksimal Rp50.000
    }
}

// Tertutup untuk modifikasi: tidak peduli jenis diskonnya apa
class Checkout {
    double finalPrice(double total, DiscountPolicy policy) {
        return total - policy.discount(total);
    }
}

public class Main {
    public static void main(String[] args) {
        Checkout checkout = new Checkout();
        List<DiscountPolicy> policies = List.of(
                new NoDiscount(), new MemberDiscount(),
                new StudentDiscount(), new VipDiscount());
        for (DiscountPolicy p : policies) {
            System.out.println(p.getClass().getSimpleName() + " -> "
                    + (long) checkout.finalPrice(200_000, p));
        }
    }
}

MemberDiscount -> 190000
StudentDiscount -> 180000
VipDiscount -> 170000


🔍 Jujur soal "tertutup"
  Pada akhirnya ada satu tempat yang harus tahu kelas mana yang dipakai untuk pelanggan tertentu (daftar pemetaan, konfigurasi, atau main). Tempat itu memang bertambah satu baris, dan itu wajar. Intinya adalah logika bisnis yang sudah teruji tidak disentuh, dan pengetahuan tentang "yang mana" dikurung di satu titik perakitan, bukan tersebar di mana-mana.




Mekanisme dan jebakan


    
  
  • Alat utama: polimorfisme lewat interface/kelas abstrak. Pola yang sering membantu: Strategy (ganti algoritma), Decorator (tumpuk perilaku), Template Method (kerangka tetap, langkah bervariasi), Observer (reaksi tambahan tanpa mengubah pemicu).
    • 
  
  • Tidak ada kode yang tertutup terhadap segalanya. Kamu hanya bisa menutup terhadap jenis perubahan yang kamu perkirakan. Menebak keliru berarti abstraksi yang salah dan rumit.
    • 
  
  • Jangan abstraksi dulu. Pegangan praktis: tulis dengan cara sederhana. Setelah perubahan pertama dari jenis itu muncul, barulah ciptakan titik variasinya ("digigit sekali, waspada selanjutnya"). Banyak tim memakai aturan tiga: duplikasi sampai tiga kali baru diabstraksi.
    • 
  
  • Bau lain yang menandakan OCP dilanggar: switch pada tipe/enum yang muncul di banyak tempat, rantai instanceof, flag boolean yang mengubah perilaku method.
    • 
  
  • switch yang sehat: satu switch di titik perakitan (factory) yang memilih implementasi masih wajar. Yang bermasalah adalah switch yang sama diulang di mana-mana.
    • 



✅ Intisari O Sediakan satu "soket" (abstraksi) di tempat kamu tahu akan ada variasi, lalu tambah fitur dengan "mencolokkan" kelas baru, bukan membongkar dinding.








L7. Liskov Substitution Principle (LSP)


📌 Definisi
  Objek dari subtipe harus bisa menggantikan objek dari supertipenya tanpa membuat program menjadi salah (Barbara Liskov, 1987/1994). Perhatikan kata kuncinya: bukan "tanpa error kompilasi", melainkan tanpa mengubah kebenaran perilaku yang diharapkan klien.



Analogi. Kiper cadangan masuk menggantikan kiper utama. Wasit, rekan satu tim, dan strategi pelatih tetap berjalan karena si pengganti bisa menangkap bola, menendang bola, dan memimpin barisan belakang, semua yang dijanjikan seorang kiper. Sekarang bayangkan "kiper" pengganti yang ternyata hanya boleh menangkap dengan satu tangan: bentuknya kiper, namanya kiper, tetapi tim tidak bisa mengandalkannya. Dalam dunia mainan ada versi lucunya: bebek karet yang bertenaga baterai. Kalau terlihat seperti bebek, bersuara seperti bebek, tetapi butuh baterai, kamu mungkin memakai abstraksi yang salah.



Mengapa "is-a" saja tidak cukup


Di kelas matematika, persegi adalah persegi panjang. Maka di kelas pemrograman banyak orang refleks menulis Square extends Rectangle. Pewarisan di OOP bukan soal definisi di kamus, melainkan soal perilaku yang bisa diandalkan. Mari kita lihat apa yang terjadi.


Main.java · persegi "adalah" persegi panjang?Java 17+
class Rectangle {
    protected int width;
    protected int height;

    void setWidth(int w)  { this.width = w; }
    void setHeight(int h) { this.height = h; }
    int area()            { return width * height; }
}

// "Persegi adalah persegi panjang", kata matematika. Kata kode?
class Square extends Rectangle {
    @Override void setWidth(int w)  { this.width = w; this.height = w; }  //!
    @Override void setHeight(int h) { this.width = h; this.height = h; }  //!
}

public class Main {
    // Kode klien yang wajar: lebar 5, tinggi 4, luas pasti 20
    static void resizeAndPrint(Rectangle r) {
        r.setWidth(5);
        r.setHeight(4);
        System.out.println(r.getClass().getSimpleName() + " -> luas = " + r.area()
                + (r.area() == 20 ? "  (OK)" : "  (SALAH! harusnya 20)"));
    }

    public static void main(String[] args) {
        resizeAndPrint(new Rectangle());
        resizeAndPrint(new Square());
    }
}

Persegi mewarisi bentuk tetapi melanggar janji: induknya menjanjikan lebar dan tinggi bisa diatur bebas satu sama lain.

class Account {
    protected double balance = 500_000;

    // Kontrak: prasyarat 0 < amount <= saldo. Pasca-syarat: saldo berkurang sebesar amount.
    void withdraw(double amount) {
        if (amount <= 0 || amount > balance) throw new IllegalArgumentException("Jumlah tidak valid");
        balance -= amount;
    }
}

        super.withdraw(amount);

}

    static void takePocketMoney(Account account) {

        System.out.println("  berhasil, sisa saldo Rp" + (long) account.balance);
    }

    public static void main(String[] args) {
        System.out.println("Account:");
        takePocketMoney(new Account());
        System.out.println("PremiumAccount:");
        try {
            takePocketMoney(new PremiumAccount());
        } catch (IllegalArgumentException e) {
            System.out.println("  GAGAL -> " + e.getMessage());
        }
    }
}

Perbaikannya hampir selalu satu dari dua: (a) jangan paksakan hubungan pewarisan, cukup bagi kontrak yang jujur lewat interface kecil; atau (b) pisahkan kemampuan opsional ke interface sendiri. // Kontrak yang jujur: "bisa dihitung luasnya", titik.
interface Shape {
    double area();
}

record Rectangle(double width, double height) implements Shape {
    public double area() { return width * height; }
}

record Square(double side) implements Shape {
    public double area() { return side * side; }
}

// Burung yang tidak bisa terbang tidak dipaksa menjanjikan fly()
abstract class Bird {
    abstract void eat();
}

interface Flyable {
    void fly();
}

class Sparrow extends Bird implements Flyable {
    void eat() { System.out.println("Pipit makan biji"); }
    public void fly() { System.out.println("Pipit terbang"); }
}

class Penguin extends Bird {
    void eat() { System.out.println("Pinguin makan ikan"); }
}

public class Main {
    static void releaseToSky(Flyable f) { f.fly(); }   // hanya menerima yang BISA terbang

    public static void main(String[] args) {
        Shape[] shapes = { new Rectangle(5, 4), new Square(4) };
        for (Shape s : shapes) System.out.println(s + " luas = " + s.area());

        releaseToSky(new Sparrow());
        // releaseToSky(new Penguin());   // tidak akan lolos kompilasi: bagus!
        new Penguin().eat();
    }
}

Cara mendeteksi & jebakan


    
  
  • Method yang melempar UnsupportedOperationException atau dibiarkan kosong di subkelas hampir selalu tanda LSP dilanggar (dan sering juga ISP).
    • 
  
  • instanceof atau pengecekan tipe sebelum memanggil method di kode klien: "kalau ini Penguin, jangan panggil fly". Klien jadi tahu subkelas, dan OCP ikut rusak.
    • 
  
  • Subkelas yang mengosongkan (override tanpa isi) perilaku induk.
    • 
  
  • Menulis tes kontrak: satu set tes untuk interface (misalnya "add lalu get mengembalikan elemen yang sama") yang dijalankan terhadap semua implementasi.
    • 
  
  • Jebakan: mewarisi hanya demi memakai ulang kode. Kalau kamu ingin memakai kode kelas lain tetapi tidak benar-benar sejenis, pakai komposisi (simpan sebagai field, delegasikan).
    • 



✅ Intisari L Subkelas boleh menambah, tidak boleh membatalkan. Sebelum menulis extends, tanyakan: "Apakah semua kode yang bekerja dengan induk tetap benar jika menerima kelas ini?" Kalau ragu, pakai interface atau komposisi.








I8. Interface Segregation Principle (ISP)


📌 Definisi
  Klien tidak boleh dipaksa bergantung pada method yang tidak ia gunakan. Lebih baik banyak interface kecil yang spesifik per kebutuhan daripada satu interface besar serba ada.



Analogi. Di Indonesia ada SIM A, B, dan C. Pengendara motor cukup memegang SIM C; ia tidak diwajibkan lulus ujian mengemudikan truk hanya karena "ada satu kartu SIM raksasa untuk semua kendaraan". Pengemudi yang mahir boleh memegang beberapa SIM sekaligus. Begitu pula kelas: ia hanya menandatangani peran yang sanggup ia penuhi, dan boleh mengambil beberapa peran.


ISP mengatasi dua rasa sakit yang berbeda. Sakit pelaksana: kelas dipaksa mengimplementasikan method yang tidak masuk akal baginya. Sakit pemanggil: kelas klien bergantung pada interface yang berisi hal yang tidak ia pakai, sehingga ikut terdampak (dikompilasi ulang, diuji ulang, di-deploy ulang) tiap kali bagian yang tidak relevan berubah.

Mekanisme dan contoh di Java

  • Interface milik klien: pecah menurut kebutuhan pemanggil. Tanyakan, "peran apa yang dibutuhkan ReportService?", bukan "apa saja yang bisa dilakukan perangkat?".

  • Penyederhanaan di Java: interface boleh extends beberapa interface, jadi peran gabungan (misalnya interface OfficeDevice extends Printer, DocScanner) tersedia untuk klien yang memang butuh keduanya.
    • 
  
  • Jebakan: memecah sampai satu method per interface secara membabi buta. Kalau dua method selalu dipakai bersama oleh semua klien (misalnya open dan close), memisahkannya hanya menambah kerumitan.

D9. Dependency Inversion Principle (DIP)


📌 Definisi
  
    
    
  1. Modul tingkat tinggi (kebijakan bisnis) tidak boleh bergantung pada modul tingkat rendah (detail teknis). Keduanya harus bergantung pada abstraksi.
    2. 
    
  2. Abstraksi tidak boleh bergantung pada detail. Detail yang bergantung pada abstraksi.
    3. 
  




Analogi. Fitting lampu standar E27: pabrik lampu dan pabrik soket sama-sama mengikuti standar ulirnya. Kamu bebas memasang lampu pijar, LED, atau neon tanpa mengubah soket, dan produsen lampu bebas berinovasi tanpa minta izin ke produsen soket. import java.util.List;

// Abstraksi dimiliki oleh sisi bisnis (high-level)
interface OrderRepository {
    void save(String order);
}

// Detail bergantung pada abstraksi (panahnya terbalik!)
class MySqlOrderRepository implements OrderRepository {
    public void save(String order) { System.out.println("MySQL: INSERT " + order); }
}

class PostgresOrderRepository implements OrderRepository {
    public void save(String order) { System.out.println("PostgreSQL: INSERT " + order); }
}

// Pengganti untuk pengujian: tanpa database sungguhan
class InMemoryOrderRepository implements OrderRepository {
    final List<String> saved = new ArrayList<>();
    public void save(String order) { saved.add(order); }
}

class OrderService {
    private final OrderRepository repository;           // bergantung pada abstraksi  //+

    OrderService(OrderRepository repository) {          // constructor injection  //+
        this.repository = repository;
    }

    void placeOrder(String order) {
        // ...aturan bisnis penting...
        repository.save(order);
    }
}

public class Main {
    public static void main(String[] args) {
        // Composition root: satu-satunya tempat yang tahu detail mana yang dipakai
        new OrderService(new MySqlOrderRepository()).placeOrder("Order#1");
        new OrderService(new PostgresOrderRepository()).placeOrder("Order#2");

        // "Unit test" tanpa database
        InMemoryOrderRepository fake = new InMemoryOrderRepository();
        new OrderService(fake).placeOrder("Order#3");
        System.out.println("Test lulus? " + fake.saved.equals(List.of("Order#3")));
    }
}

    public long now() { return fixed; }
}

class ReceiptService {
    private Clock clock;

        service.setClock(new FixedClock(1_800_000_000L));

10. Kelimanya Bekerja Bersama


Sampai di sini kamu mungkin merasa kelima prinsip itu seperti lima nasihat terpisah. Sebenarnya mereka lebih mirip lima sisi dari satu bangun: masing-masing menutup celah yang dibiarkan terbuka oleh yang lain. Gambar di bawah memperlihatkan hubungannya; angka pada garis dijelaskan di tabel sesudahnya.








  
#PasanganHubungannya

  
1SOKelas yang dipecah per aktor lebih mudah "ditutup": perubahan satu aktor hanya menyentuh satu kelas.

  
2OLOCP mengandalkan polimorfisme; LSP menjamin objek pengganti tidak merusak klien. Tanpa LSP, "perluasan" berubah menjadi bug.

  
3LIInterface gemuk memaksa implementasi palsu (method kosong atau melempar exception), yang berarti pelanggaran L. Interface kecil menghindarinya.

  
4IDDIP meminta kita bergantung pada abstraksi; ISP memastikan abstraksi itu ramping sehingga layak dijadikan tumpuan.

  
5DSSetelah kelas dipecah (S), banyak bagian kecil perlu dirangkai. DIP dan injeksi merakitnya tanpa mengikat satu sama lain.

  
6ODTitik variasi OCP adalah sebuah abstraksi; DIP menentukan siapa pemiliknya dan ke mana arah panahnya.

  
7SIKeduanya memotong berdasarkan "siapa yang berkepentingan": S untuk kelas (menurut aktor), I untuk interface (menurut klien).




🔗 Efek domino dalam kode buruk
  Satu keputusan buruk jarang berhenti sendiri: interface gemuk (ISP) → method palsu yang melempar exception (LSP) → klien menambahkan instanceof untuk menghindarinya (OCP) → logika bisnis mengenal kelas konkret (DIP) → kelas pengatur membengkak (SRP). Itulah mengapa memperbaiki satu mata rantai sering membuat yang lain ikut membaik.



Cara berpikir ringkas yang bisa kamu pakai saat code review: S memotong, I merampingkan, D mengarahkan panah, O menyediakan titik variasi, dan L menjaga agar semua titik variasi itu dapat dipercaya.

Pola desain (design patterns) adalah resep siap pakai yang hampir selalu merupakan penerapan SOLID dalam bentuk tertentu. Kalau SOLID adalah aturan tata letak dapur, maka pola adalah denah dapur untuk masakan tertentu.

Contoh paling dekat yang sudah kamu pakai tanpa sadar adalah List.sort. Ia tidak pernah dimodifikasi sejak ditulis, tetapi perilakunya terus diperluas oleh siapa pun yang menyerahkan sebuah Comparator:


Main.java · OCP di pustaka standarJava 17+
import java.util.ArrayList;
import java.util.Comparator;
import java.util.List;

record Product(String name, double price) { }

public class Main {
    public static void main(String[] args) {
        List<Product> menu = new ArrayList<>(List.of(
                new Product("Kopi", 25_000), new Product("Teh", 8_000), new Product("Susu", 15_000)));

        // List.sort() tidak pernah diubah, tetapi perilakunya diperluas lewat Comparator (Strategy + OCP)
        menu.sort(Comparator.comparingDouble(Product::price));    //+
        System.out.println("Termurah dulu : " + menu);

        menu.sort(Comparator.comparing(Product::name));           //+
        System.out.println("Urut abjad    : " + menu);
    }
}

SOLID dan pengujian


Pengujian adalah alat ukur yang jujur untuk kualitas desain: kode yang sulit diuji hampir selalu melanggar salah satu prinsip. Gunakan sebagai uji cepat:



  
"Aku harus menyalakan database untuk menguji perhitungan"→ DIP dilanggar. Bisnis menggenggam detail. Ekstrak interface, injeksikan fake.

  
"Tesku punya 40 baris persiapan"→ SRP dilanggar. Kelas terlalu banyak tanggung jawab sehingga butuh terlalu banyak "dunia" agar bisa hidup.

  
"Aku harus mengubah tes lama tiap menambah fitur"→ OCP dilanggar. Perilaku baru tidak datang sebagai kode baru yang bisa diuji sendiri.

  
"Satu set tes sama harus lolos untuk semua implementasi"→ Itulah tes kontrak untuk LSP. Jalankan satu suite terhadap semua implementasi sebuah interface.




🧰 Istilah singkat Stub: objek palsu yang mengembalikan jawaban tetap. Fake: implementasi sederhana yang sungguhan bekerja (misalnya database di memori). Mock: objek palsu yang juga memeriksa bagaimana ia dipanggil. Pustaka seperti Mockito membantu membuat mock, tetapi tanpa DIP pun mereka tidak punya titik untuk menyelipkan mock tersebut.








13. Jebakan & Over-engineering


Orang yang baru paham SOLID sering melewati fase berbahaya: semua kode tiba-tiba harus punya interface. SOLID adalah alat untuk membuat perubahan murah, bukan tujuan hidup. Kode yang dipecah menjadi 40 kelas untuk fitur yang tak pernah berubah justru lebih mahal dirawat daripada satu kelas besar yang jelas.



  
🧩Interface untuk segalanyaUserService + UserServiceImpl hanya karena "kata buku begitu". Jika hanya ada satu implementasi dan tak ada alasan ia berganti, interface itu beban. Mulailah dari batas arsitektur (bisnis ↔ infrastruktur).

  
💥Ledakan kelasSatu fitur kecil menyebar di 12 file kecil sehingga pembaca kehilangan alur. Kelas kecil itu bagus hanya jika namanya jelas dan hubungannya mudah ditelusuri.

  
🔮Abstraksi prematurMenebak variasi yang belum ada (YAGNI: You Aren't Gonna Need It). Abstraksi yang salah lebih mahal daripada duplikasi sementara. Tunggu sampai perubahan nyata pertama.

  
🙏Menyembah prinsipMendebat "ini melanggar S atau I?" selama sejam sementara fiturnya terlambat. Ukuran akhirnya satu: apakah perubahan berikutnya jadi lebih murah dan lebih aman?

  
🌳Pewarisan berlapisHirarki lima tingkat yang membuat orang harus membuka lima file untuk memahami satu method. Pilih komposisi dan interface kecil.

  
🎣Konstruktor dengan 11 parameterPada kode yang memakai DI, ini tanda kelas tersebut memiliki terlalu banyak tanggung jawab (S). Jangan lawan dengan "objek parameter" saja; pecahkan kelasnya.

    Subtipe tidak boleh membatalkan janji induk. Maka jangan janjikan write() di tempat yang tidak semua penyimpanan sanggup menulis. Mulailah dari interface paling kecil.
    

    ✅ Jawaban
    

    Main.java · jawabanJava 17+
    interface ReadableStorage {
    String read();
}

interface WritableStorage extends ReadableStorage {
    void write(String text);
}

class FileStorage implements WritableStorage {
    private String content = "isi awal";
    public String read()           { return content; }
    public void write(String text) { content = text; }
}

class ReadOnlyStorage implements ReadableStorage {            // tidak pernah menjanjikan write()
    public String read() { return "data arsip"; }
}

public class Main {
    static void backup(WritableStorage storage) {             // hanya menerima yang BISA ditulis
        storage.write("cadangan");
        System.out.println("Isi sekarang: " + storage.read());
    }

    static void show(ReadableStorage storage) {
        System.out.println("Membaca: " + storage.read());
    }

    public static void main(String[] args) {
        backup(new FileStorage());
        show(new ReadOnlyStorage());
        // backup(new ReadOnlyStorage());   // ditolak compiler. Bug tertangkap sebelum program jalan.
    }
}
    

    Keluaran (dijalankan dengan JDK 21)
    Isi sekarang: cadangan
Membaca: data arsip
    

    


    Latihan 4 · IPekerja dan robot
    

    Tugas: Robot dipaksa melempar exception di eat(). Pecah Worker menurut peran, lalu buat Canteen yang hanya menerima yang bisa makan.
    

    Main.java · kode awalJava 17+
    interface Worker {
    void work();
    void eat();
}

class Human implements Worker {
    public void work() { System.out.println("Manusia bekerja"); }
    public void eat()  { System.out.println("Manusia makan siang"); }
}

class Robot implements Worker {
    public void work() { System.out.println("Robot bekerja"); }
    public void eat()  { throw new UnsupportedOperationException("Robot tidak makan"); }   //!
}

public class Main {
    public static void main(String[] args) {
        Worker[] team = { new Human(), new Robot() };
        for (Worker w : team) w.work();
        for (Worker w : team) {
            try { w.eat(); } catch (UnsupportedOperationException e) { System.out.println("Gagal: " + e.getMessage()); }
        }
    }
}
    

    💡 Petunjuk
    Dua kemampuan, dua interface. Human boleh menandatangani keduanya.
    

    ✅ Jawaban
    

    Main.java · jawabanJava 17+
    interface Workable { void work(); }
interface Eatable  { void eat();  }

class Human implements Workable, Eatable {
    public void work() { System.out.println("Manusia bekerja"); }
    public void eat()  { System.out.println("Manusia makan siang"); }
}

class Robot implements Workable {
    public void work() { System.out.println("Robot bekerja"); }
}

class Canteen {
    void lunchBreak(Eatable... diners) {            // kantin hanya peduli yang bisa makan
        for (Eatable d : diners) d.eat();
    }
}

public class Main {
    public static void main(String[] args) {
        Human budi = new Human();
        Robot r2 = new Robot();
        for (Workable w : new Workable[] { budi, r2 }) w.work();
        new Canteen().lunchBreak(budi);
    }
}
    

    Keluaran (dijalankan dengan JDK 21)
    Manusia bekerja
Robot bekerja
Manusia makan siang

    Tugas: Ubah NotificationService supaya (1) kanal bisa diganti ke email tanpa mengedit layanan, dan (2) bisa diuji tanpa benar-benar mengirim pesan. Buktikan dengan sebuah fake.

}

class NotificationService {
    private final SmsSender sender = new SmsSender();            //!

        // Bagaimana menguji NotificationService tanpa benar-benar mengirim SMS?
    }

    💡 Petunjuk
    Buat interface dari sudut pandang NotificationService ("aku butuh sesuatu yang bisa mengirim pesan"), lalu suntikkan lewat konstruktor.
    

    ✅ Jawaban
    

    Main.java · jawabanJava 17+
    import java.util.ArrayList;
import java.util.List;

interface MessageSender {                                          //+
    void send(String to, String text);
}

class SmsSender implements MessageSender {
    public void send(String to, String text) { System.out.println("SMS ke " + to + ": " + text); }
}

class EmailSender implements MessageSender {                       // kanal baru tanpa menyentuh NotificationService
    public void send(String to, String text) { System.out.println("Email ke " + to + ": " + text); }
}

class NotificationService {
    private final MessageSender sender;                            //+

    NotificationService(MessageSender sender) {                    //+
        this.sender = sender;
    }

    void notifyUser(String user, String text) {
        sender.send(user, text);
    }
}

class FakeSender implements MessageSender {                        // untuk pengujian
    final List<String> log = new ArrayList<>();
    public void send(String to, String text) { log.add(to + "|" + text); }
}

public class Main {
    public static void main(String[] args) {
        new NotificationService(new SmsSender()).notifyUser("0812-xxxx", "Paketmu tiba");
        new NotificationService(new EmailSender()).notifyUser("budi@contoh.id", "Paketmu tiba");

        FakeSender fake = new FakeSender();
        new NotificationService(fake).notifyUser("tes", "halo");
        System.out.println("Tes lulus? " + fake.log.equals(List.of("tes|halo")));
    }
}
    

    Keluaran (dijalankan dengan JDK 21)
    SMS ke 0812-xxxx: Paketmu tiba
Email ke budi@contoh.id: Paketmu tiba
Tes lulus? true
